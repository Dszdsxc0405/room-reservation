## 分支依赖与合并顺序

当前提交关系为 `main` (`949bb60`) → `chore/container-dev-env` (`638ba5c`) → `chore/app-scaffold` (`fd7eae8`) → `chore/ci-tests`。`chore/app-scaffold` 的交付范围只是 Web 与单后端骨架，不必等待业务功能完成。

1. 先由人完成 `chore/container-dev-env` 对 `main` 的评审与合并。
2. 再由人完成 `chore/app-scaffold` 对 `main` 的评审与合并。
3. 最后评审并合并 `chore/ci-tests` 到 `main`。在前两支未合并时，可暂以 `chore/app-scaffold` 为本分支 PR 的目标来审查 CI 独有改动；分支 push 会触发 CI，但当前工作流只对指向 `main` 的 PR 触发 `pull_request` 检查。前置分支合并后将 PR 目标改为 `main`，核对完整检查通过，再合并。
4. CI 合入后，将 `Backend checks` 和 `Web checks` 设为 `main` 的必需检查，再让已并行开发的功能分支陆续进入合并评审。业务功能不需等前置分支评审才开始开发。

各分支的合并均由人执行；agent 不自行合并或处理跨分支冲突。
