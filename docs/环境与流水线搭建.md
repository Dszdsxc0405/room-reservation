# 环境与流水线搭建

> 状态：**执行指南，容器内开发工具、本地数据库和应用骨架已完成部分搭建，尚未整体验收**。目标主机为 Debian GNU/Linux 12 (bookworm)。开发和本地测试使用 Linux 原生进程与数据库；测试、生产演示的部署使用 Linux Docker 镜像。当前实际结果见[容器开发环境搭建记录](task-reports/2026-11-11-容器开发环境搭建.md)和[应用脚手架记录](task-reports/2026-11-12-应用脚手架.md)，后续结果填入[搭建记录模板](环境与流水线搭建记录_模板.md)。业务和技术依据分别是[需求基线 V1](07_需求基线_V1.md)、[技术方案 V1](13_技术方案_V1.md)及[后续步骤](15_需求分析后续步骤.md)。此前的 Windows 只读检查是历史记录，不能代替 Linux 检查。

## 目标与停止条件

完成后应有：私有 GitHub 仓库；开发、测试、生产三套逻辑隔离环境和独立 PostgreSQL 数据库；提交及合并请求自动构建、测试；主分支检查通过后自动部署**全部**测试模块；指定负责人按版本标签手动发布生产；可核验的备份、回退和运行记录。现阶段只有应用骨架，以下步骤按[实际记录](task-reports/2026-11-12-应用脚手架.md)逐项判断，不预先报完成。

任何一步缺少预期结果，就记录实际输出并停在该步；不凭猜测修改系统设置或进入后续发布。安装软件、更改系统服务、账号、权限或防火墙前先征求机器所有者同意。`⚠️` 表示会改变主机、远端仓库或业务数据，执行前核对目标环境。

| 阶段 | 完成后应看到什么 |
|---|---|
| 只读检查与工具准备 | 记录 Debian、Java、Maven、Node、PostgreSQL 及资源的真实状态；部署前再核验 Docker Engine 与 Compose |
| 私有仓库 | GitHub 显示 Private，历史已推送，仓库无凭据或个人数据 |
| 三套环境 | 每套有独立数据库；服务健康，测试数据不会进入生产 |
| CI | 分支提交和 PR 自动检查；故意失败的测试阻止合并与部署 |
| 发布 | CI 成功后测试环境更新全部模块；生产只能由负责人手动触发 |
| 回退 | 备份可恢复，上一版本应用可重新启动并通过健康检查 |

## 1. 只读检查：确认 Linux 主机状态

在 Debian 12 的终端进入仓库，运行下列**只读**命令，逐项将版本、可用内存、磁盘空间、端口和报错记入搭建记录。先记录仓库在 Linux 上的实际路径；命令不存在可记“命令不可用”，继续检查软件包与文件位置，不据此断言已安装或卸载。

```sh
pwd
cat /etc/os-release
uname -m
git status --short --branch
free -h
df -h .
ss -lnt
java -version
mvn -version
node --version
npm --version
psql --version
pg_config --version
pg_lsclusters
git --version
```

部署工具另做只读检查；此时缺少 Docker 记为“部署待准备”，不会阻断原生开发与本地测试：

```sh
docker version
docker compose version
```

判定：Git 工作区已核对；系统确为预期 Debian 12；Java 是 21，Node 满足所选 Vite 版本要求；PostgreSQL 客户端与服务端版本、现有实例和数据库要分别核实。Docker 只在部署阶段必需，届时 `docker version` 须同时显示 Client 和 Server，`docker compose version` 须可用。量测单个后端 JVM、Web、原生数据库和部署容器的**实际**占用；记录可用磁盘、预计备份空间与端口占用。单机逻辑隔离仍会共享资源，若不足先决定扩容或分时运行并写明限制。1000 个虚拟用户仅是后期压测示例。

## 2. 准备原生工具与私有仓库

⚠️ **主机设置：** 若缺少 Java 21、Maven、与所选 Vite 兼容的 Node、Git 或 PostgreSQL，先核对现有用途和安装方式，再征得机器所有者同意。Java、Node 优先使用用户目录下固定版本；Maven 使用仓库根目录已有的 `./mvnw`，npm 依赖放在项目目录并由锁文件固定。PostgreSQL 开发实例优先使用专用非 root 账号、用户可控数据目录和本机监听端口；不要改动机器上已有的数据库服务。若需要安装 Debian 软件包、启动系统服务或更改权限，逐项记录影响并先征求同意。`uv` 只管理 Python 虚拟环境，项目没有 Python 辅助工具时不必安装；它不能隔离 Java、Node 或 PostgreSQL。[uv 环境说明](https://docs.astral.sh/uv/pip/environments/)、[PostgreSQL initdb](https://www.postgresql.org/docs/current/app-initdb.html)。

⚠️ **部署工具：** 在准备部署测试环境前，再依[Docker 官方 Debian 安装说明](https://docs.docker.com/engine/install/debian/)核对并经同意安装 Docker Engine、CLI、Buildx 与 Compose 插件；开发和本地测试不依赖 Docker。安装前查现有 Docker/Podman 及防火墙规则，不自动卸载冲突软件或修改防火墙。Docker 组成员拥有近似 root 权限，不为省去 `sudo` 而自动加组；部署账号的权限单独核对并记录。[Docker 权限说明](https://docs.docker.com/engine/install/linux-postinstall/)。

⚠️ **远端发布：** 由仓库负责人在 GitHub 创建**私有**仓库，并核对可见性、成员和权限；检查 `git status`、`.gitignore`，确认没有密码、`.env`、数据库备份或个人数据，再添加 `origin` 并推送现有历史。保存远端地址和第一次推送结果。六名成员按[协作流程](../CONTRIBUTING.md)使用独立分支、非作者评审和跨模块确认；在 GitHub 设置可用的主分支保护及必需的 CI 检查。私有仓库的 GitHub 环境审批功能受套餐限制，**不要把它当成生产发布的唯一审批门**，见[官方说明](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments)。

## 3. 规划三套环境（生成配置前先填表）

由执行者在搭建记录中给每套环境填入实际主机/访问地址、端口、数据库名、数据目录或卷、配置文件位置、负责人和可用内存。数据库密码和访问令牌只记**保存位置**，不得写入仓库或记录正文。开发数据库与开发服务首选只监听 `127.0.0.1`；需要让他人访问时再确定网络、反向代理与权限。

| 环境 | 运行方式 | 数据 | 用途与发布方式 |
|---|---|---|---|
| 开发 | Debian 原生进程 | 独立开发库和数据目录；本地自动测试另用可重建测试库 | VS Code、Java/Maven、Node/npm 在主机上运行 |
| 测试 | 部署时使用 Compose 项目 `rr-test` | 独立测试库、卷和测试数据 | 主分支检查通过后自动部署全部模块 |
| 生产演示 | 部署时使用 Compose 项目 `rr-prod` | 独立生产库、卷和演示数据 | 指定负责人按 tag 手动发布 |

开发的原生 PostgreSQL 实例可包含相互独立的开发库和本地测试库，但须使用不同凭据并禁止测试脚本连接开发库。CI 使用自己的临时数据库；部署测试和生产演示各用独立 PostgreSQL 容器及持久卷，不能把三个 schema 或同一个数据库称作三套环境。记录 Linux 主机上的实际内存、磁盘和容器限额；资源不足时先调整容量或分时运行，不在未验证前合并测试与生产数据。无论哪种环境，模块 M1/M2/M3/D 共享所属环境的库，各自只修改本模块负责的表，用户 RBAC 不能替代[数据归属约定](12_六人分工与数据归属_V1.md)。

仓库已有[开发配置示例](../config/application-db.example.properties)及对应忽略规则；真实开发/部署密钥放在仓库外。部署阶段再增加 `infra/compose/compose.yml`、服务 Dockerfile、迁移与种子数据脚本；`.env.*.local` 与本地数据目录加入 `.gitignore`。Compose 不写固定 `container_name`、固定共享卷名或跨环境通用数据库地址；对外端口分别规划。用 `-p rr-test`、`-p rr-prod` 明确项目名，使容器、默认网络和卷按项目区分，见[Compose 项目说明](https://docs.docker.com/compose/intro/compose-application-model/)。部署前执行 `docker compose -p rr-test --env-file <测试配置> -f infra/compose/compose.yml config` 和相应生产配置检查解析结果，确认数据库目标、卷及端口没有串环境。`<...>` 是待替换的本机真实路径。

⚠️ **数据卷：** 正常停止优先用 `docker compose -p <项目名> -f infra/compose/compose.yml stop`；不要将 `down -v`、`volume prune` 或数据库删除写进日常脚本。任何清理须先核对项目名、卷名与备份。

## 4. 数据库和服务的最小联通

目前已验证单个后端使用开发库配置启动并通过 HTTP 健康检查，Web 占位首页可访问；内部模块接口、测试库联调及以下业务检查仍待实现。运行命令见[仓库 README](../README.md)。

1. 先在 Debian 原生开发环境中启动 PostgreSQL、单个后端和 Web；Web 通过 HTTP 访问后端，M1/M2/M3/D 在后端内部通过公开接口协作。健康检查应区分“进程运行”和“数据库/依赖可用”。核对开发库名、监听地址、日志及后端健康接口；随后在独立测试库上运行本地联调。测试部署就绪后再验证 `rr-test` 的 Compose 状态、日志和健康检查；生产演示环境最后启动。
2. 每个模块维护自己业务表的 Flyway 迁移。所有脚本在一个环境中按**统一版本顺序**执行；从空数据库完整重放，重复执行幂等种子脚本，并验证不会混入其他环境数据。迁移在新版本后端启动前执行；失败时停止部署，不靠人工直接改生产表。
3. 验证三个环境的库名、连接目标、后端版本、Web 页面和站内消息分别独立。运行一笔测试预约后只应在测试环境出现；生产演示库不得含开发测试数据。端到端验证至少经过真实 Web 与后端 HTTP 请求；后端内部协作由集成测试覆盖。

## 5. CI 自动检查（待实施）

在 `.github/workflows/ci.yml` 配置 `push`（任务分支和主分支）及指向主分支的 `pull_request` 触发，**使用 GitHub 托管的 Linux runner** 执行原生代码检查，避免 PR 内容在带有部署权限的 Debian 机器上直接运行。固定 Java 21 和与 Vite 兼容的 Node 版本；当前已有的构建、类型检查和 lint 命令见[协作流程](../CONTRIBUTING.md)。业务测试加入后也须进入 CI。CI 在 runner 上使用临时 PostgreSQL 数据库验证 Flyway 从空库重放及关键数据库约束，不能连接开发、部署测试或生产库。任何一项失败则 CI 失败，不能合并或部署；保存失败截图/日志链接和修复后的成功运行。

原生检查通过后才构建部署用的 Linux 镜像，并把镜像摘要关联 Git 提交 SHA；测试与生产部署同一份已检查镜像，不在发布时临时改源码。不要让 PR 工作流读取生产配置、部署令牌或运行部署 job。GitHub 对[自托管 runner 的安全风险](https://docs.github.com/en/actions/reference/security/secure-use)有明确说明。

## 6. 测试自动部署与生产手动发布

⚠️ **部署权限：** 仅在私有仓库的受保护主分支部署工作流上注册 Debian 机器的专用 self-hosted runner。先让 runner 以预定部署账号执行 `docker version` 和 `docker compose version`，确认该账号有预期权限；不能因为交互终端可用就认定后台 runner 可用。Docker socket 访问相当于高权限操作，不把 PR job 分配到这台 runner。机器关机、Docker 服务停止或 runner 离线时部署会等待或失败；记录这一运行限制。按[GitHub 指南](https://docs.github.com/en/actions/how-tos/manage-runners/self-hosted-runners/add-runners)注册，runner 配置和令牌不得进入仓库。

测试部署只接受主分支 **CI 成功** 的提交：锁定同机部署窗口，记录部署前版本，运行迁移后更新测试环境的 Web 与单个后端，等待健康检查，通过真实 HTTP 跑一条覆盖多个内部模块的冒烟流程；失败保留日志并标记失败。部署时联调者暂停判断环境故障，避免把切换窗口误报为业务失败。每次记录 SHA、镜像标识、迁移版本和模块清单。

⚠️ **生产发布：** 负责人先核对已评审的 tag、对应 CI 与测试部署结果，再由**人工手动触发**发布工作流；不得随主分支提交自动发布生产。GitHub 私有仓库若当前套餐没有环境必需审批，则使用仅限授权成员的手动触发、发布前人工核对和记录签名/姓名作为审批证据；不可写成“GitHub 已自动强制双人审批”。同机部署用一把部署锁，避免测试和生产同时改动共享 Docker 资源；具体 Actions `concurrency` 语义按[官方文档](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency)核对，并在演练中验证两次部署不会并行。生产使用自身配置、数据库与卷，迁移前先做可验证的备份，发布后检查后端、Web 和关键 AC。

## 7. 回退演练与交付判据

⚠️ **生产数据：** 发布前保存数据库备份、当前 tag 与镜像标识；先在隔离环境演练从备份恢复，确认文件可读且恢复后可查询。应用回退使用上一可用镜像/标签，**数据库迁移不默认可逆**：若新迁移不兼容旧应用，先用向后兼容迁移方案或经验证的备份恢复计划，不执行未经演练的自动降级。回退同样经过人工确认并记录操作人、时间、前后版本与健康结果。

| 验收点 | 应留下的证据 |
|---|---|
| 三套环境隔离 | 原生开发库与本地测试库独立；部署测试与生产使用不同 Compose 项目名、连接目标、数据库与卷；测试数据不出现在生产 |
| 自动检查 | PR 和主分支运行链接；故意失败的检查阻断合并与部署 |
| 测试自动部署 | 主分支成功后 Web 和含 M1/M2/M3/D 的单个后端全部更新及真实 HTTP 冒烟结果 |
| 生产人工发布 | tag、负责人核对、手动触发记录、发布前备份和发布后健康结果 |
| 数据与回退 | 空库重放迁移、种子脚本重复执行、备份可恢复、应用回退演练 |

搭建结束后把 Debian 主机上的实际命令、版本、地址、端口、链接、失败处理和未完成项写入[搭建记录](环境与流水线搭建记录_模板.md)的副本；只有证据齐备的项才写“完成”。后续开发任务再依[质量约定](quality.md)与 BP/AC 加入业务验收。参考：[PostgreSQL 备份](https://www.postgresql.org/docs/current/backup-dump.html)、[Docker Compose 命令](https://docs.docker.com/reference/cli/docker/compose/)。
