# 环境与流水线搭建

> 状态：**执行指南，尚未搭建**。适用于当前 Windows 电脑；由人或 agent 按步骤执行，并把真实结果填入[搭建记录模板](环境与流水线搭建记录_模板.md)。本轮只编写文档。业务和技术依据分别是[需求基线 V1](07_需求基线_V1.md)、[技术方案 V1](13_技术方案_V1.md)及[后续步骤](15_需求分析后续步骤.md)。

## 目标与停止条件

完成后应有：私有 GitHub 仓库；开发、测试、生产三套逻辑隔离环境和独立 PostgreSQL 数据库；提交及合并请求自动构建、测试；主分支检查通过后自动部署**全部**测试模块；指定负责人按版本标签手动发布生产；可核验的备份、回退和运行记录。现阶段没有应用代码，以下标为“代码就绪后”的步骤不能预先报完成。

任何一步缺少预期结果，就记录实际输出并停在该步；不凭猜测修改系统设置或进入后续发布。`⚠️` 表示会改变本机、远端仓库或业务数据，执行前核对目标环境。

| 阶段 | 完成后应看到什么 |
|---|---|
| 只读检查与工具准备 | 记录真实版本和资源；Docker 客户端、服务端及 Compose 均可用 |
| 私有仓库 | GitHub 显示 Private，历史已推送，仓库无凭据或个人数据 |
| 三套环境 | 每套有独立数据库；服务健康，测试数据不会进入生产 |
| CI | 分支提交和 PR 自动检查；故意失败的测试阻止合并与部署 |
| 发布 | CI 成功后测试环境更新全部模块；生产只能由负责人手动触发 |
| 回退 | 备份可恢复，上一版本应用可重新启动并通过健康检查 |

## 1. 只读检查：确认电脑能承担哪些环境

在 PowerShell 打开仓库，运行下列**只读**命令，逐项将版本、可用内存、磁盘空间和报错记入搭建记录。命令不存在可记“未安装/路径未配置”，不要据此断言已安装或卸载。

```powershell
Set-Location 'S:\VSCode\room-reservation'
git status --short --branch
Get-ComputerInfo | Select-Object WindowsProductName, WindowsVersion, OsTotalVisibleMemorySize
Get-PSDrive -PSProvider FileSystem | Select-Object Name, Free
wsl --version
docker version
docker compose version
java -version
mvn -version
node --version
npm --version
```

判定：Git 工作区已核对；Windows、WSL 2 和 Docker Desktop 满足[官方 Windows 安装要求](https://docs.docker.com/desktop/setup/install/windows-install/)；`docker version` 同时显示 Client 与 Server；Java 是 21，Node 满足所选 Vite 版本要求。还要量测四个 JVM 服务、Web 和数据库**实际**占用，不从“Docker 可启动”推断三套系统可同时运行。记录可用磁盘、预计数据库备份空间与端口占用；若不足，先决定调整资源或分时运行，再明确哪些环境可用。1000 个虚拟用户仅是后期压测示例，不是此处的通过线。

## 2. 安装基础工具和建立私有仓库

⚠️ **本机设置：** 若缺少 WSL 2 或 Docker Desktop，由机器所有者依[Docker 官方步骤](https://docs.docker.com/desktop/setup/install/windows-install/)安装；开启虚拟化、Windows 功能或重启前先保存工作。选择 Linux 容器及 WSL 2 后再次运行 `wsl --version`、`docker version`、`docker compose version`。Java 21、Maven、Node 与 Git 缺少时从各自官方渠道安装；每次安装后重开终端复查版本。不要在不明现有软件用途时卸载或覆盖旧版本。

⚠️ **远端发布：** 由仓库负责人在 GitHub 创建**私有**仓库，并核对可见性、成员和权限；检查 `git status`、`.gitignore`，确认没有密码、`.env`、数据库备份或个人数据，再添加 `origin` 并推送现有历史。保存远端地址和第一次推送结果。六名成员按[协作流程](../CONTRIBUTING.md)使用独立分支、非作者评审和跨模块确认；在 GitHub 设置可用的主分支保护及必需的 CI 检查。私有仓库的 GitHub 环境审批功能受套餐限制，**不要把它当成生产发布的唯一审批门**，见[官方说明](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments)。

## 3. 规划三套环境（生成配置前先填表）

由执行者在搭建记录中给每套环境填入访问地址、端口、数据库名、数据卷、配置文件位置、负责人和可用内存。数据库密码和访问令牌只记**保存位置**，不得写入仓库或记录正文。首选只绑定本机地址；需要让他人访问时再确定网络与权限。

| 环境 | Compose 项目名 | 数据 | 用途与发布方式 |
|---|---|---|---|
| 开发 | `rr-dev` | 独立开发库、卷和测试数据 | 本地启动，供日常开发 |
| 测试 | `rr-test` | 独立测试库、卷和测试数据 | 主分支检查通过后自动部署 |
| 生产演示 | `rr-prod` | 独立生产库、卷和实际演示数据 | 指定负责人按 tag 手动发布 |

默认先评估三个 PostgreSQL 容器能否与所需服务同时运行；资源不足时可采用**一个 PostgreSQL 实例内三个独立数据库**，但仍要分别配置库名、连接凭据、备份和迁移目标。选择、实测依据及限制写入记录；不能把三个 schema 或同一个数据库称作三套环境。无论选哪种，模块 M1/M2/M3/D 共享所属环境的库，各自只修改本模块负责的表，用户 RBAC 不能代替[数据归属约定](12_六人分工与数据归属_V1.md)。

代码就绪后，在仓库增加 `infra/compose/compose.yml`、三套非机密配置示例、服务 Dockerfile、迁移与种子数据脚本；真实 `.env.*.local` 放入 `.gitignore`。Compose 不写固定 `container_name`、固定共享卷名或跨环境通用数据库地址；对外端口分别规划。用 `-p rr-dev/rr-test/rr-prod` 明确项目名，让容器、默认网络和卷按项目区分，见[Compose 项目说明](https://docs.docker.com/compose/intro/compose-application-model/)。启动前执行 `docker compose -p rr-test --env-file <测试配置> -f infra/compose/compose.yml config` 检查解析结果，并确认输出没有意外指向生产库。`<...>` 要替换为本机真实路径，不是原样复制。

⚠️ **数据卷：** 正常停止优先用 `docker compose -p <项目名> -f infra/compose/compose.yml stop`；不要将 `down -v`、`volume prune` 或数据库删除写进日常脚本。任何清理须先核对项目名、卷名与备份。

## 4. 代码就绪后：数据库和服务的最小联通

1. 为四个后端服务、Web、PostgreSQL 编排启动；Web 通过统一入口访问后端，服务间走 HTTP。健康检查应区分“进程运行”和“数据库/依赖可用”。先只启动开发环境，验证 `docker compose ... ps`、日志及各服务健康接口，再启动测试和生产演示环境。
2. 每个模块维护自己业务表的 Flyway 迁移。所有脚本在一个环境中按**统一版本顺序**执行；从空数据库完整重放，重复执行幂等种子脚本，并验证不会混入其他环境数据。迁移在新版本服务启动前执行；失败时停止部署，不靠人工直接改生产表。
3. 验证三个环境的库名、连接目标、服务版本、Web 页面和站内消息分别独立。运行一笔测试预约后只应在测试环境出现；生产演示库不得含开发测试数据。首次联通至少经过真实 HTTP 请求，不以函数直调替代跨模块联调。

## 5. 代码就绪后：CI 自动检查

在 `.github/workflows/ci.yml` 配置 `push`（任务分支和主分支）及指向主分支的 `pull_request` 触发，**使用 GitHub 托管 runner** 执行代码检查，避免 PR 内容在这台电脑上直接运行。固定 Java 21 和与 Vite 兼容的 Node 版本；各服务执行 Maven 测试与构建，Web 执行 `npm ci`、TypeScript 类型检查、测试与构建。确切命令以实际 `pom.xml`、`package.json` 为准，建成后回填[协作流程](../CONTRIBUTING.md)。用临时 PostgreSQL 验证 Flyway 从空库重放及关键数据库约束。任何一项失败则 CI 失败，不能合并或部署；保存失败截图/日志链接和修复后的成功运行。

把代码构建出的镜像/制品关联 Git 提交 SHA；测试与生产部署同一份已检查制品，不在发布时临时改源码。不要让 PR 工作流读取本机生产配置、部署令牌或运行部署 job。GitHub 对[自托管 runner 的安全风险](https://docs.github.com/en/actions/reference/security/secure-use)有明确说明。

## 6. 测试自动部署与生产手动发布

⚠️ **本机执行权限：** 仅在私有仓库主分支部署工作流上注册当前电脑的专用 self-hosted runner。先让 runner 以预定账号执行 `docker version` 和 `docker compose version`，确认它在该账号下可访问 Docker；不能因为交互终端可用就认定后台 runner 可用。电脑休眠、关机或 Docker 未启动时，部署会等待或失败；记录这一运行限制。按[GitHub 指南](https://docs.github.com/en/actions/how-tos/manage-runners/self-hosted-runners/add-runners)注册，runner 配置和令牌不得进入仓库。

测试部署只接受主分支 **CI 成功** 的提交：锁定同机部署窗口，记录部署前版本，运行迁移后更新测试环境的 Web 与 M1/M2/M3/D，等待全部健康检查，通过真实 HTTP 跑一条跨模块冒烟流程；失败保留日志并标记失败。部署时联调者暂停判断环境故障，避免把切换窗口误报为业务失败。每次记录 SHA、镜像标识、迁移版本和模块清单。

⚠️ **生产发布：** 负责人先核对已评审的 tag、对应 CI 与测试部署结果，再由**人工手动触发**发布工作流；不得随主分支提交自动发布生产。GitHub 私有仓库若当前套餐没有环境必需审批，则使用仅限授权成员的手动触发、发布前人工核对和记录签名/姓名作为审批证据；不可写成“GitHub 已自动强制双人审批”。同机部署用一把部署锁，避免测试和生产同时改动共享 Docker 资源；具体 Actions `concurrency` 语义按[官方文档](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency)核对，并在演练中验证两次部署不会并行。生产使用自身配置和数据库，迁移前先做可验证的备份，发布后检查四服务、Web 和关键 AC。

## 7. 回退演练与交付判据

⚠️ **生产数据：** 发布前保存数据库备份、当前 tag 与镜像标识；先在隔离环境演练从备份恢复，确认文件可读且恢复后可查询。应用回退使用上一可用镜像/标签，**数据库迁移不默认可逆**：若新迁移不兼容旧应用，先用向后兼容迁移方案或经验证的备份恢复计划，不执行未经演练的自动降级。回退同样经过人工确认并记录操作人、时间、前后版本与健康结果。

| 验收点 | 应留下的证据 |
|---|---|
| 三套环境隔离 | 不同项目名/连接目标/数据库与卷；测试数据不出现在生产 |
| 自动检查 | PR 和主分支运行链接；故意失败的检查阻断合并与部署 |
| 测试自动部署 | 主分支成功后 Web、M1/M2/M3/D 全部更新及真实 HTTP 冒烟结果 |
| 生产人工发布 | tag、负责人核对、手动触发记录、发布前备份和发布后健康结果 |
| 数据与回退 | 空库重放迁移、种子脚本重复执行、备份可恢复、应用回退演练 |

搭建结束后把实际命令、版本、地址、端口、链接、失败处理和未完成项写入[搭建记录](环境与流水线搭建记录_模板.md)的副本；只有证据齐备的项才写“完成”。后续开发任务再依[质量约定](quality.md)与 BP/AC 加入业务验收。参考：[PostgreSQL 备份](https://www.postgresql.org/docs/current/backup-dump.html)、[Docker Compose 命令](https://docs.docker.com/reference/cli/docker/compose/)。
