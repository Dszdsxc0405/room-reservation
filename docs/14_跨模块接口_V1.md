## 共同约定

### 请求与重试

跨模块写入操作携带唯一操作编号、来源模块与来源 ID、资源 ID、受影响时段、原因和发起人。提供方按操作编号去重，重复执行返回同一结果；进程中断后先查询持久结果再重试。

### 生效与失败

M2 终审、M3 报修和 D 管理计划在相关模块处理完成前不能标记最终成功。若操作无法一次完成，保留“处理中”记录并在恢复后重试，不显示已完全生效。M1 在事务内完成限制写入和个人预约取消；若终审最终失败，M2 解除本申请已写入的限制。尚未完成的报修或管理计划须补齐跨模块处置，或撤销自身待生效变更。单进程、单数据库下能否将相关写入合入同一事务，应在实现时按锁顺序和通知副作用确定。

### 数据边界与并发

各模块只修改本模块负责的数据，并在提交时重验相关状态：

- M1 协调同一教室的预约与限制写入；存在报修或管理关闭限制时，拒绝新的整室占用。
- M2 终审前重验其他整室批准、D 开放配置及 M3 报修状态；最终确认时检查申请仍未被撤销。
- M3 报修提交前确认资源没有未结束工单；进入维修中前等待正在使用的安排结束。

整室终审与教室报修或关闭计划同时发生时，按先完成的操作处理：终审先完成，后续报修或关闭取消批准；报修或关闭先完成，终审不能通过。

### 通知与限制解除

业务结果确认后投递站内消息；投递失败保留记录重试。解除限制只删除对应来源，不自动恢复此前取消的预约或申请。

### 开发前细化与联调

细化内部 Java 接口的参数、结果、权限和错误语义；若采用持久重试，还需约定重试上限。联调覆盖上述两种先后顺序、并发抢座、重复执行及进程中断后的恢复。
