# 技术方案 V1

> 2026-11-06。依据[需求基线](07_需求基线_V1.md)、[六人分工](12_六人分工与数据归属_V1.md)及课程任务书。技术选型已确定；尚未搭建环境、开发或测试。真实用户量和峰值并发暂无数据，不据此虚构容量指标。

曾比较 TypeScript/NestJS 与 Java/Spring Boot 两条后端路线：两者都能运行四个独立 HTTP 服务，也都需解决相同的预约并发和跨服务失败问题。需求负责人已选择 **Java/Spring Boot**，前端选择 **Vue/Vite**。技术语言的选择不替代数据库约束和接口确认。

| 部分 | 方案 | 选择原因 |
|---|---|---|
| Web | Vue 3 + Vite + TypeScript，单个 Web 应用 | 覆盖学生、管理员、维修员的页面和站内消息入口 |
| 后端 | Java 21 + Spring Boot；M1、M2、M3、D 四个独立 HTTP 服务 | 与已定数据主责一致，满足真实跨模块网络调用要求 |
| 数据 | 每套环境一套 PostgreSQL；四个独立 schema 和账号 | 当前电脑即可承载；每个服务只读写自己的数据，跨模块通过 HTTP |
| 数据变更 | 各模块用 Flyway 管理本模块 schema，初始化数据脚本可重复执行 | 从空库重建并追溯结构版本 |
| 运行 | Docker Compose；测试与演示环境在当前电脑上分别隔离 | 便于整体启动、联调及按版本回退 |
| 代码与流水线 | 私有 GitHub 仓库、GitHub Actions；当前电脑运行部署用 Runner | 推送及合并请求自动构建测试；电脑在线时测试环境自动部署，演示环境经负责人批准后发布并可回退 |

这里的 schema 是一套 PostgreSQL 中分开的数据区域：每个模块有自己的账号和区域，只能通过接口使用其他模块的数据。当前电脑每套环境运行一套数据库即可，避免为四个模块分别运行数据库服务。

## 并发与一致性

- 本系统尚无可用于估算吞吐量的真实数据。已知的高风险是**同座位或同学生同时预约**、**整室终审与个人预约同时提交**、**报修或管理变更与新预约同时发生**。先保证业务结果正确，之后再用实测决定是否扩容。
- M1 是座位可约性的最终判断方。查询结果仅供展示，提交时重新读取 D 的当前配置并在 M1 事务内检查限制；同一教室的预约与限制变更按固定顺序串行处理。数据库约束兜底，保证同座位、同学生的有效预约不出现重叠。自然日按学校本地时间计算，时段以 `[开始, 结束)` 判断相交。
- M2 整室终审、M3 报修提交、D 关闭/缩短开放时间计划都须收到受影响模块的处理确认后，才对用户显示最终成功。跨服务暂态标记为“处理中”，按操作编号查询结果并重试；不可把一次网络超时当成成功。站内消息失败单独重试，不回滚已确认的业务结果。
- 同一来源的限制可重复提交但只生效一次；解除时只解除该来源，M1 仍重新判断其他限制。取消的预约或整室申请不会因限制解除而自动恢复。

## 当前边界

不引入消息队列、缓存或额外数据库实例；现有需求没有证明它们必要。四服务的接口和失败处理见[跨模块接口 V1](14_跨模块接口_V1.md)。具体版本号、机器资源、流水线配置和容量基线在环境搭建时核实并锁定，不属于本阶段已验证结果。

技术依据：[Spring Boot](https://docs.spring.io/spring-boot/system-requirements.html)、[Vue/Vite](https://vuejs.org/guide/quick-start.html)、[PostgreSQL 时段约束](https://www.postgresql.org/docs/current/sql-createtable.html)、[Flyway](https://docs.spring.io/spring-boot/how-to/data-initialization.html)、[Docker Compose](https://docs.docker.com/get-started/docker-concepts/running-containers/multi-container-applications/)。
