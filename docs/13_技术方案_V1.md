> 2026-11-06 重审选型依据；2026-11-11 确认开发、测试、生产三套逻辑隔离环境，并将执行平台调整为 Debian GNU/Linux 12：原生开发与测试，部署阶段使用 Linux Docker 镜像；2026-11-19 按任务发起人决定改为单个 Spring Boot 后端。依据[需求基线](07_需求基线_V1.md)、[数据归属](12_六人分工与数据归属_V1.md)和[接口边界](14_跨模块接口_V1.md)。容器内开发工具与本地数据库已按[搭建记录](task-reports/2026-11-11-容器开发环境搭建.md)准备，应用骨架见[脚手架记录](task-reports/2026-11-12-应用脚手架.md)；尚无业务代码、CI 或部署环境。“1000 人同时预约”是压测示例，不是性能验收线。

## 从需求确定评判标准

BP-01 要求同座位、同学生的有效预约时段不重叠；BP-06 的整室终审会取消冲突座位预约；BP-07 的教室或座位报修提交后立即限制新约。页面查询与最终提交之间可能出现变化，因此**服务器提交时必须重验，数据库必须守住不重约的底线**。M1/M2/M3/D 在一个 Spring Boot 后端内通过公开 Java 接口交接；开发、测试、生产环境在 Linux 机器上逻辑隔离，各使用独立数据库。选型重点是这些写入和交接能否正确实现，以及单机负载能否实测，而不是只比较框架宣传的吞吐量。

### Web：Vue/Vite、React/Vite、Thymeleaf

座位筛选、审批和维修状态、站内消息都需要多角色交互页面；它们不需要搜索引擎收录。Spring MVC + Thymeleaf 可以生成页面，但多处局部状态更新仍要编写浏览器脚本；单页应用更贴合这组交互。Vue/Vite 与 React/Vite 都可实现，**无法从预约并发量推断谁更快或更正确**。React/Vite 还要自行组合路由等应用结构；Vue 官方脚手架可直接选择 Vite、TypeScript 和 Router，因此本项目采用 **Vue 3 + Vite + TypeScript**。这是交付复杂度的取舍，不是并发性能结论。[Vue 项目脚手架](https://vuejs.org/guide/quick-start)、[React/Vite 项目说明](https://react.dev/learn/build-a-react-app-from-scratch)、[Spring 模板支持](https://docs.spring.io/spring-boot/reference/web/servlet.html)。

一个 Web 应用访问一个 Spring Boot 后端。浏览器展示的可约结果只是查询时快照；预约提交、权限和冲突由后端重新判断。Vite 不负责 TypeScript 类型检查，构建流水线还须运行类型检查。[Vue TypeScript 说明](https://vuejs.org/guide/typescript/overview)。

### 后端：NestJS、Spring MVC、Spring WebFlux

本系统的写入路径是“校验规则 → 短事务内锁定资源、写预约或限制 → 提交”，并有整室审批、报修、签到超时等定时操作。候选技术都能接收并发 HTTP 请求；**1000 个连接不等于 1000 笔能同时写库的事务**。真正的瓶颈可能是 HTTP 排队、数据库连接池或热点座位的锁等待，必须测量后判断。

NestJS/Node.js 的事件循环适合非阻塞 I/O，但长时间阻塞回调会拖慢其他请求；它同样不能代替数据库约束。Spring WebFlux 可减少等待 I/O 时占用的线程，但若数据库仍用 JDBC，就不能充分发挥全链路非阻塞的优势；改用 R2DBC 和响应式事务又增加一套数据访问模型。这里需要直接管理 PostgreSQL 事务与锁，所以选择 **Java 21 + 单个 Spring Boot/Spring MVC 应用 + JDBC**：用本地事务包住一次预约或限制写入，用可配置的 HTTP 工作线程和数据库连接池控制并发。这个选择更契合当前写入模型，**不构成“Spring 一定比 NestJS 更快”或“现有电脑已能承载 1000 人”的证明**。后端 JVM 的内存开销也要在部署前核实。[Node.js 事件循环](https://nodejs.org/learn/asynchronous-work/dont-block-the-event-loop)、[Spring MVC/WebFlux 取舍](https://docs.spring.io/spring-framework/reference/web/webflux/new-framework.html)、[R2DBC 事务](https://docs.spring.io/spring-framework/reference/data-access/r2dbc.html)、[Spring 事务](https://docs.spring.io/spring-framework/reference/data-access/transaction/declarative/annotations.html)、[Spring Boot 线程与连接池配置](https://docs.spring.io/spring-boot/appendix/application-properties/)。

四个业务模块运行在同一进程、使用同一数据库；跨模块操作可由应用服务编排并设计为同一个短事务。具体事务边界、锁顺序、通知投递和异常恢复在接口细化时确定。报修提交必须让 M1 写入限制并取消受影响预约，教室报修还须让 M2 处置整室申请；D 保存关闭计划也须使 M1/M2 完成相应处置，不能留下已显示生效却仍能新约的状态。中断后的重试和来源解除遵守[接口边界](14_跨模块接口_V1.md)。

### 数据：PostgreSQL、MySQL、SQLite

SQLite 一次只允许一个写入者，不适合作为多人集中提交预约的生产数据库。MySQL/InnoDB 支持并发事务；若用它，可把整点座位预约拆成逐小时占用记录，分别对“座位+小时”和“学生+小时”建唯一键，但整室批准、维修和管理变更仍要处理跨时段相交。PostgreSQL 的时间范围与排斥约束可直接表达“同座位或同学生的**有效**预约区间不得重叠”，减少这部分规则对应用锁的依赖。因此选择 **PostgreSQL**；这是约束表达和实现可核验性的优势，并非未经测试的吞吐量优势。[SQLite 写入限制](https://www.sqlite.org/isolation.html)、[MySQL/InnoDB 锁](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking.html)、[PostgreSQL 范围与排斥约束](https://www.postgresql.org/docs/current/rangetypes.html)。

开发、测试、生产三套环境各用独立 PostgreSQL 数据库，不按业务模块拆账号或数据区。开发环境在 Debian 12 上使用独立的原生 PostgreSQL 库；本地和 CI 的测试使用专用、可重建的测试库；部署后的测试环境和生产演示环境各用自己的容器、数据库和持久卷。它们能否在一台机器上同时运行，须以实际内存、磁盘和端口检查为准。各模块只修改自己负责的业务表；用户 RBAC 只约束用户操作，不能替代模块间的数据归属约定。座位可约性变化频繁，缓存可加速查询但不能决定提交结果；首版先用索引和事务，压测后再判断是否需要 Redis。迁移脚本由所属模块维护，发布流水线按统一版本顺序在后端启动前执行。范围约束可按以下思路落地，学生维度同理；具体表名和状态值在设计表结构时确定：

```sql
-- 示意：m1_booking.period 为 tstzrange，表和状态名待设计
CREATE EXTENSION IF NOT EXISTS btree_gist;
ALTER TABLE m1_booking ADD CONSTRAINT no_seat_overlap
  EXCLUDE USING gist (seat_id WITH =, period WITH &&)
  WHERE (status = 'EFFECTIVE');
```

## 最终技术栈

| 部分 | 方案 |
|---|---|
| Web | Vue 3、Vite、TypeScript；统一 Web 入口 |
| 后端 | Java 21、单个 Spring Boot/Spring MVC 应用、JDBC；M1/M2/M3/D 为内部业务模块 |
| 数据 | 开发、测试、生产环境各用独立 PostgreSQL 数据库；Flyway 统一版本迁移 |
| 原生开发与测试 | Debian 12 上用 VS Code、Java 21/Maven、Node/npm 和 PostgreSQL 运行与测试；项目数据、依赖、配置和端口分开管理 |
| 运行与发布 | 部署时用 Linux Docker 镜像及 Compose 隔离测试、生产演示环境；计划用私有 GitHub + Actions，测试自动部署、生产人工批准及回退 |

`uv` 创建的是 Python 虚拟环境，只在项目实际引入 Python 辅助脚本时使用；它不管理 Java、Node 或 PostgreSQL。本项目目前不要求安装或使用 `uv`。Java、Node 优先使用用户目录下的固定版本；Maven 依赖使用项目约定的版本和用户级缓存，Web 依赖由锁文件安装；PostgreSQL 使用专用数据库、受限账号和独立的数据位置。这样减少对系统默认工具和其他项目的影响，但同机进程仍会占用 CPU、内存、磁盘及端口，不能把逻辑隔离当成物理隔离。[uv 虚拟环境](https://docs.astral.sh/uv/pip/environments/)、[PostgreSQL 数据目录](https://www.postgresql.org/docs/current/app-initdb.html)。

开发时一个 Java 后端和 Vite 在 Linux 主机上运行，后端使用开发库；本地集成测试使用测试库。CI 在 GitHub 托管的 Linux runner 上运行构建、类型检查、测试和空库迁移验证。检查通过后才构建并固定镜像标识；同一份镜像先部署到 `rr-test`，再经人工核对版本标签部署到 `rr-prod`。两套部署各有独立配置、网络、数据库卷与备份。开发库不接入部署容器，PR 代码不在有生产权限的自托管 runner 上执行。生产镜像不携带开发机的 JDK、Node 缓存、数据库文件或密钥。[Docker Engine for Debian](https://docs.docker.com/engine/install/debian/)、[GitHub 自托管 runner](https://docs.github.com/en/actions/how-tos/manage-runners/self-hosted-runners/add-runners)。

## 并发场景与处理

| 场景 | 竞态或压力表现 | 处置方法 |
|---|---|---|
| 大量查询和提交同时到达 | HTTP 请求排队、连接池耗尽；页面仍显示旧的“可约” | 为查询条件建索引并分页；限制 HTTP 工作线程、数据库连接池及等待超时；提交时重验。 |
| 两人抢同一座位，或一人同时订两座位 | 各请求都读到“未占”，写出重叠有效预约 | M1 在事务内按座位和学生协调写入；PostgreSQL 对有效预约设座位+时段、学生+时段两道排斥约束。冲突方明确失败。 |
| 不同座位提交与整室终审同时发生 | 全室一律串行会压低吞吐；不协调则批准时漏取消新预约 | M1 自有的教室协调记录：座位提交取共享锁、整室限制取独占锁；不同座位并行。限制写入与未来冲突预约取消在 M1 同一事务内完成。 |
| 教室/座位报修撞上新约 | 报修后仍订入，或漏取消未来预约 | 教室报修取教室独占锁，单座位报修取座位锁；M1 事务内按工单来源写限制并取消未来预约。已签到使用可到结束；M3 待 M1/M2 确认后才显示报修成功。 |
| 关闭教室或缩短开放时间 | 管理计划已保存却仍订入受影响时段，或整室批准未取消 | D 按生效时段要求 M1 处理个人预约、M2 处理整室申请；M1 的教室级变更取独占锁。两模块确认后计划才显示保存成功。 |
| 重叠整室申请同时终审 | 两笔都被批准 | M2 对同教室批准时段做事务内重验和数据库冲突约束；仅一笔成功，另一笔自动驳回。与报修/关闭并发时按已定完成顺序处理。 |
| 签到与未签到清理同时执行 | 已签到却被取消或重复记违约 | M1 按服务端时间和当前状态做条件更新；开始后 15 分钟含端点可签到，15 分 01 秒起未签到才取消并记一次。 |
| 操作中断或重复执行 | 已完成部分处理，重试后重复取消或通知 | 写入带唯一操作编号；重试前查持久结果，未确认前显示“处理中”。待发送通知写入持久记录，投递失败重试；解除限制只按来源解除。 |

这里的教室、座位锁由 M1 自己维护，不直接锁 D 的主数据表；事务应短，锁获取顺序固定。不同座位可并行，热点座位需要等待或得到冲突结果。PostgreSQL 的[共享/独占行锁](https://www.postgresql.org/docs/current/explicit-locking.html)与[排斥约束](https://www.postgresql.org/docs/current/rangetypes.html)提供最终保护。

开发后用两个**示例**压测：1000 个虚拟用户分散预约不同座位，观察吞吐与排队；1000 个虚拟用户争同一座位，验证至多一笔成功。记录响应时间、超时、数据库连接与锁等待、CPU 和内存，再判断是否需要调线程/连接池或增加机器资源。现阶段不承诺容量数值。
