# 单任务开发与分阶段联调原则

> 适用范围：本项目 M1、M2、M3、D 等模块的开发任务。本文规定默认工作范围与分阶段验证方式；需求基线、BP/AC、模块规则、接口约定和提交评审要求仍须遵守。

## 一句话原则

**默认一次只实现任务指定的责任范围。** 先用明确的最小契约和本地替身（fake）完成该范围的规则与测试；真实依赖由其负责人另行实现，之后逐个接入并验证。开发 B 的业务规则，不要求先把 A、E、F 全部实现完；会影响结果或锁顺序的接口含义仍须尽早核对。

## 默认工作边界

1. **范围由任务书决定**：任务须写明负责人、角色、BP/AC、允许修改的文件或包、完成判据。A/B/E/F 是成员责任代号，不是四个业务模块；A 与 B 都涉及 M1，也不能因此互相改对方负责的文件。
2. **不自行扩任务**：未获明确任务授权，不启动其他实现 agent，不替 A/E/F 补真实实现、迁移或调度器。已有代码可以只读参考；位于同一分支不等于允许修改。发现依赖缺口，先用符合契约的测试替身继续做本任务，并把真实接入列为后续任务。
3. **接口先核对语义**：可在本任务范围内定义供自身测试使用的端口或 fake；不要擅自定义别的模块的生产接口、表或业务规则。确需变更公共接口、事务或锁序时，提交具体方法/字段与受影响场景，等待相关模块负责人复核；用户可见结果未定时交需求负责人决定。
4. **明确停点**：本任务的测试可完成时，交付测试结果和未接入清单，然后停止；不因“顺便打通端到端”继续修改其他责任范围。只有任务发起人明确扩大范围，才进入真实跨模块接入阶段。独立评审和人工验收照常进行。

## 五个阶段

| 阶段 | 主要工作 | 可以用什么依赖 | 完成标志 |
|---|---|---|---|
| 1. 定范围与最小契约 | 写明本模块负责的业务结果、输入输出、错误语义；列出需要别的模块提供的最少事实或操作 | 简短接口草案、字段说明 | 依赖的含义足以编写本模块测试；未定的业务规则有明确负责人 |
| 2. 单模块实现 | 只写本模块的规则、状态转换和本模块数据；用可控的替身覆盖外部返回值 | fake、stub、mock；固定时钟与内存数据 | 本模块的成功、失败、边界、重复调用等测试通过 |
| 3. 本任务自身集成 | 若本任务负责存储，则接入其真实适配器、迁移和约束；若不负责，则保留 fake 并登记依赖 | 其他责任范围仍可用 fake | 当前责任范围的真实部分在专用测试库中通过适用测试；未接入项明确标注 |
| 4. 逐个跨模块接入 | 先核对契约，再把外部 fake 换成真实公开接口；每接一个就验证一次 | 已实现的真实模块接口 | 字段、异常、事务与锁序一致；跨模块测试通过 |
| 5. 端到端验收 | 从真实入口走完整用户流程，并检查失败恢复 | 全部相关真实模块 | BP/AC、权限、并发、消息与可见结果经独立复核和人工验收 |

这些阶段是验证层次，不要求每阶段都开一个分支或安排一组人。进入下一阶段也不自动扩大文件权限；其他责任范围暂时没人开发时，保留清楚的接口草案与替身即可。

## 什么是“最小契约”

最小契约只回答本模块开发必须知道的问题：

1. **调用什么**：方法、参数、返回值及字段含义。例如 B 需要读取哪条预约、按哪个时间判断签到窗口。
2. **失败怎样表达**：查不到、编码错误、编码事实不可用、重复请求，分别是什么结果或异常。
3. **谁拥有数据**：M1 写预约与违约；D 写编码事实和消息记录。一个模块不能为图方便直接改另一个模块的表。
4. **何时需要事务或锁**：哪些事实必须同事务提交，取锁顺序是什么，提交后才能做什么。

先约定这些语义即可。实现类、数据库表和完整框架可以随后由各自负责人完成。若契约会改变用户看到的结果，交需求负责人决定；若改动公共接口，交受影响模块负责人复核。agent 的意见不能代替成员确认。

## fake、stub、mock 分别能帮什么忙

- **fake**：有简化行为的本地实现。例如内存预约存储，可以保存“已签到”状态，让 B 连续调用两次并检查第二次的结果。
- **stub**：按场景返回预设答案。例如编码校验在一个测试中返回“正确”，在另一个测试中返回“错误”。
- **mock**：记录调用并核对必要的交互。例如确认超时取消只请求写入一次通知事件。

它们都是**测试辅助**，不代表 A/E/F 的生产实现已经完成，也不能证明 PostgreSQL 行锁、真实事务或投递可靠。优先测试业务结果；只有调用次数或先后顺序本身属于契约时，才检查交互细节。跨模块的替身应依照约定接口编写，避免 B 测试依赖 D 的私有类。

## 用本次 M1 签到说明

B 可以先用内存预约存储、固定时钟和假编码校验器，开发并测试以下顺序：查预约与本人身份 → 查取消和已签到 → 查签到时间 → 校验教室编码 → 标记已签到。测试还可覆盖超时取消、重复执行以及签到与超时竞争时的预期结果。这一步不要求 B 修改 A 的存储、E 的编码表或 F 的消息投递器。B 工作树里已有 A/E/F 代码，也不改变 B 本轮的修改范围。

**另开或明确授权真实接入任务时**，再分别验证：

1. **接 A**：`BookingLifecycleStore.withLockedBooking` 和 `markCheckedIn` 是否在同一事务中使用真实预约行锁；用 PostgreSQL 测试并发与边界秒。
2. **接 E**：按预约使用日和学校时区取得编码事实；遵守已确认的取锁顺序，即协调锁 → D 编码事实锁 → M1 预约行锁；保留 B 原有的结果判断顺序。缺码、编码发布和唯一性等未定规则先交负责人决定。
3. **接 F**：在超时取消的业务事务内记录通知事件，提交后再投递；投递失败不应把已提交的签到或取消结果改写成失败。提醒调度可单独开发和验收，不阻塞“仅签到”。

**B 分支当前状态（2026-11-20）**：A 已有 M1 预约存储、锁和 V1 迁移；E 已有 D 编码事实的锁定读取和 V2 迁移，但编码生成、发布等流程尚未完成；F 已有 D 消息记录与投递的基础接口、实现和 V3 迁移，但提醒调度等业务入口尚未完成。B 已有规则及使用内存存储、假编码校验器的测试；真实接口的完整接入和端到端验收仍是后续工作。此前并行推进 A/E/F，是当次任务主动要求准备真实依赖，**不是以后开发任一责任范围都必须照搬的前置步骤**。

## 什么时候需要多个开发者或 agent 并行

只有任务发起人明确要求多责任范围同时交付，且每人或每个 agent 有独立分支、工作树与文件范围、公共契约足够明确，并安排了合并与复核，才并行实现。若只是开发一个责任范围的规则，先集中在该范围。需要别的负责人配合时，优先请求**接口结论或简短复核**，无需默认要求对方同时实现整套模块。

并行不等于免除最后联调。合并后的代码必须再次验证，因为各分支单独通过测试，不能保证组合后也通过。本次 E 测试曾泄漏 PostgreSQL 连接的 `search_path`，单独运行能通过，和 A 同进程测试才暴露问题，就是一个例子。

## 提交与验收的最小检查

- **单模块交付**：说明实现了哪些 BP/AC，展示实际 diff、单模块测试结果和未实现的外部依赖；由独立人员复核。fake 测试通过时，只称“规则测试通过”。
- **模块接入交付**：说明使用了哪个公开接口、事务和锁要求；展示专用数据库与跨模块测试结果。公共接口、schema 变更请相关模块负责人复核。
- **主线合并前**：按 `CONTRIBUTING.md` 完成人工验收、合并请求评审和自动检查。不要把构建通过、替身测试通过或 agent 结论写成 BP/AC 人工验收通过。

以后发起任务可以直接写：“本次只开发 B 负责的 M1 签到规则。业务代码只允许改 `seatbooking.internal.application` 及其测试，另可更新必需的任务报告和需求追踪；A/E/F 的现有实现只读，外部依赖用符合既有契约的 fake。不要启动其他实现 agent，不改 A/E/F 生产代码、迁移或公共接口。交付 B 的规则测试、实际 diff 和待联调清单；真实接入与跨模块测试另开任务。若发现业务规则或契约冲突，列出场景和文件交负责人决定。”
