# 需求分析完成后的步骤

> 业务需求基线 V1、六人分工、技术方案、跨模块接口及开发规则索引均已整理；[本轮待决策问题](待决策问题_领域与模块规则.md)已处理。第 2 步的容器内开发工具、本地数据库和应用骨架已准备，见[环境搭建记录](task-reports/2026-11-11-容器开发环境搭建.md)及[脚手架记录](task-reports/2026-11-12-应用脚手架.md)；CI、部署环境及后续步骤仍待完成。

1. **开工准备**：六名实际成员认领 A～F；建立私有 GitHub 仓库并推送本地历史；约定分支、评审和共享数据变更规则。若出现新的业务结果问题，先由需求负责人决定并同步决策记录、BP/AC 与模块规则。
2. **环境与流水线**：在 Debian 12 机器先核实 Java、Node、PostgreSQL 和资源条件，原生运行开发与本地测试；部署前再核实 Docker Engine 和 Compose。建立逻辑隔离的开发、测试、生产环境，各用独立数据库。在私有仓库配置 Linux runner 上的提交/合并请求自动构建测试、失败阻断；部署用 runner 在线时更新测试环境的 Web 和单个后端，避免部署期间误报。生产环境按版本标签经负责人批准后发布并演练回退。
3. **接口细化**：按[跨模块接口 V1](14_跨模块接口_V1.md)补齐内部 Java 接口的参数、结果、权限、错误语义及中断后恢复方式；另行设计 Web 与后端的 HTTP API。四个内部模块先用公开接口完成最小联通；各模块负责所属表的迁移脚本。
4. **并行开发**：A/B 做 M1，C 做 M2，D 做 M3，E/F 做公共层 D；按 BP 的 AC 实现页面、业务和必要测试。共享接口或数据库变更先交叉评审。
5. **整体联调与验收**：重点跑并发预约、签到超时、整室审批占座、报修提交下架、管理计划取消安排、来源解除、消息失败重试；从空库重放迁移，并通过真实 HTTP 请求走完整前后端流程，内部模块协作通过集成测试验证。对照 AC 人工验收，记录未通过项和修复结果。
6. **交付**：完成生产环境发布与回退演练，保存版本标签、构建测试、迁移、联调及人工验收记录。

技术参数与容量以环境核实和测试结果为准；若业务结果要变，先由需求负责人决定，再更新决策记录、受影响 BP/AC 和基线版本。
