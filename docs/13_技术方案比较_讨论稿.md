# 技术方案比较：讨论稿

> 状态：待需求负责人选择。六人均为全栈工程师，但共同熟悉的技术栈、代码托管和测试/生产环境尚未提供。依据：[任务书](Pj-任务书.pdf)与[分工决定](12_六人分工与数据归属_V1.md)。

| 方案 | 组成 | 适用判断 |
|---|---|---|
| A：统一 TypeScript | React/Vite 前端；M1/M2/M3/D 各自运行 NestJS HTTP 服务；PostgreSQL；Flyway 版本化 SQL 迁移；Docker Compose | 团队熟悉 TypeScript 时，可减少前后端语言切换；仍需认真处理跨服务一致性 |
| B：Java 后端 | Vue/Vite 前端；四个 Spring Boot HTTP 服务；PostgreSQL；Flyway 迁移；Docker Compose | 团队熟悉 Java/Spring 时，沿用其数据访问与工程化习惯；前后端使用两种语言 |

两案都让四个模块以**独立进程通过公开 HTTP 接口调用**；数据库可先共用一个 PostgreSQL 实例，但各模块只写自己负责的 schema，不直接改其他模块的数据。前端为一个 Web 应用，React 与 Vue 可以独立于后端选择。最终技术栈和数据库部署方式须结合现有环境决定。

## 两案共同的落地条件

- M1 独占个人预约和时段限制的修改权；并发提交必须在数据库层保证同座位重叠时段至多一笔有效预约。PostgreSQL 的范围类型与排斥约束可作为实现候选。
- M2 终审、M3 报修和 D 管理变更在调用其他模块失败时，不能向用户显示已完全生效的结果；接口需要操作编号、重复调用保护、失败重试和可查询的处理中状态。具体状态与补偿流程留待接口设计。
- 提交与合并请求触发构建和测试；测试环境自动部署全部模块；生产环境人工批准、可回退。迁移脚本随代码提交，从空库可重放；种子数据幂等。流水线平台取决于代码托管与现有服务器。

参考：[NestJS HTTP 服务](https://docs.nestjs.com/first-steps)、[Spring Boot](https://docs.spring.io/spring-boot/system-requirements.html)、[Vite](https://vite.dev/guide/)、[PostgreSQL 时段约束](https://www.postgresql.org/docs/current/sql-createtable.html)、[Flyway 迁移](https://documentation.red-gate.com/fd/migrations-271585107.html)、[Docker Compose](https://docs.docker.com/get-started/docker-concepts/running-containers/multi-container-applications/)。
