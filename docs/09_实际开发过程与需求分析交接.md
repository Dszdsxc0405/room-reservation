## 一、我们修正了什么判断

本系统不适合按“分析完 BP-01 → 单独把 BP-01 开发定型 → 再分析 BP-02”推进。之前将 BP 当作近乎独立的开发单位，低估了交互。座位在某时段能否预约，同时受个人预约、签到超时释放、整教室审批、维修下架、管理员关闭/调整以及系统配置影响；M2 和 M3 的结果又必须与 M1 发生真实集成。只把 BP-01 的页面、表和接口先做定型，后续很可能改动状态表示、数据所有者及跨模块契约。

**当前项目决定不采用增量交付。** 适合本项目的顺序是：先分析全部 BP 的关键业务交互，形成经审查的需求基线；据此确定模块责任、技术栈、数据归属和跨模块契约；六人按共同设计分工开发、持续集成，最后按约定的系统范围做整体联调、验收与交付。前期不必穷尽每个页面和所有异常，但必须解决会改变核心业务事实、并发不变量、模块边界和交付结果的政策。开发过程内部可以拆任务、提交代码和测试；这些内部步骤不被定义为分批业务交付。

六人协作指南曾按用户要求回退，后来又按现行七 BP 编号和开发顺序修订。**`全部BP横向影响扫描_历史讨论_V0.md` 与 `首轮架构与开工门槛_历史讨论_V0.md` 是先前讨论增量交付时留下的历史产物，现已去掉数字前缀、保留原始内容。接手 Agent 不读取、不引用、不更新，也不据此推导当前规则、开工门槛或架构。**现行业务输入为课程任务书、`08_业务决策记录_V0.md`、`00`～`06` 的 BP 正文；`07` 仅作为待复核的候选索引。本文件和修订后的指南说明当前方法，不代替业务决策。

## 二、开发前依次完成的工作

| 顺序 | 要做的事 | 产物 / 完成判断 | 为什么 |
|---|---|---|---|
| 1. 核对来源和范围 | 读任务书，列 SC 与全部候选 BP、角色、交付约束；区分原文、用户决定、分析推断和未知问题 | BP 索引、R/Q 来源、待确认范围 | 防止把 Agent 的猜想写成业务事实；M1/M2/M3/D 是课程模块约束，不等于 BP 划分 |
| 2. 检查全部 BP 的交互 | 基于任务书与各 BP 正文，逐项识别触发、业务结果、读写的对象、状态变化、事件先后；检查共享资源和重叠时段 | 在现行 BP、决策记录及候选基线中形成可审查的关联与 Q；不使用历史扫描文件 | 在架构前确认 BP-02/03/05/06/07 如何反向影响 BP-01 |
| 3. 逐条细化并核对 BP | 对每条候选流程写主线、分支、对象/事件、R/Q、CAP、UC、可交付 US 和可观察 AC；需求负责人逐条确认或修正 | `00`～`06`，及规则→US/AC、对象变化→事件的反向覆盖 | 能把已知规则变成可检验的结果，同时暴露未决定的政策 |
| 4. 持续做跨 BP 回写 | 以同一座位/教室、重叠时段、相反事件顺序、多个限制来源为线索，检查一个 BP 的新结论是否改变其他 BP；更新 Q、R、AC 和索引 | `07`、`08` 与受影响 BP 同步；未决结果不能伪装成已覆盖，不更新历史文件 | 避免局部文件自洽而整个系统不一致 |
| 5. 形成需求基线 V1 | 明确已确认规则与项目开发范围、待决 Q 的处理及影响、US/AC；请需求负责人审查 | 版本化 V1 与对应决策记录；当前 `07` 只是候选 | 开发者必须知道系统要实现什么、哪些结果仍不能自行决定 |
| 6. 划定模块责任 | 用 BP×CAP 使用关系和课程 M1/M2/M3/D 约束，讨论模块职责、教室/座位与预约及各限制来源的数据所有者、最终可约性判断责任，记录方案与理由 | CAP→模块映射、D 归属、数据主责和重大决策记录 | 多处使用的能力不必然属于 D；一项业务事实不能由多组无约束地改写 |
| 7. 比较技术方案并定契约 | 基于已划定的责任比较团队熟悉度、网络调用、迁移、CI、测试部署与回滚成本；确定接口/事件的触发、字段、时间语义、失败/重试、重复处理、撤销、来源追溯 | 技术选择、架构、跨模块契约和关键风险的短验证 | 技术栈服务于课程交付和业务一致性；契约先于六人并行实现 |
| 8. 按责任分工开发 | 对 US 检查业务结果与 AC、相关 Q、模块/数据所有者、契约、验收人和验证方式；六人按统一设计开发并持续集成 | 工作分工、接口测试、构建与部署记录；阻塞项回到需求决策 | 内部任务可以并行，不能由各组自行补政策或形成相互矛盾的实现 |
| 9. 整体联调、验收与交付 | 按约定的系统范围运行跨模块网络链路、AC、迁移、部署与回滚验证；修复缺陷并回写状态 | 完整系统的集成与人工验收证据、可追溯版本 | 当前方案是系统范围内统一交付，不安排按 BP 或 US 分批交付 |

说明：第 2～4 步可以反复回环，分析 BP-06 后若发现审批对 BP-01 的新影响，立即修订相关文件。第 5 步的基线是**可版本化的共同设计依据**；变更须记录原因和受影响范围。技术原型和内部联调可用于验证风险，但不构成分批业务交付。若任务书中的功能拟不纳入本次系统交付，须作为范围变更明确决定，不能仅写“以后再做”。

## 三、首版设计必须覆盖的交接

| 交接或共享事实 | 首轮要回答的问题 | 尚未确定时的处理 |
|---|---|---|
| 学生预约和可约性 | 谁维护有效预约，谁在提交时最终判断座位/学生重叠占用及整点、开放、资格限制？ | 不让 M1 和 D 分别计算互相矛盾的结果 |
| 签到超时释放 | BP-02 何时取消、如何解除个人占用并重新评价后续整点时段？并发签到与取消如何只生效一种结果？ | R-18 已有业务结果，需契约及验证；发送失败不影响取消/违约 |
| 整教室审批 | 待审不占座；最终获批让 M1 拒绝新约、追溯来源；已有个人预约怎样处理？ | Q-01 已定：获批时取消冲突的未来个人预约并通知，不记违约；跨模块契约待架构阶段 |
| 报修限制与维修 | 报修提交时教室工单限制全室座位、座位工单只限制该座位；验收只解除本工单限制 | Q-02/12/25 已定；不能用一个“可用”布尔值覆盖另一来源 |
| 空间主数据与配置 | BP-03 管教室/座位与可用性，BP-05 统一配置开放时间；参数和权限如何影响旧记录？ | Q-04/05/17/20/21 已决定；跨模块契约待架构阶段 |
| 观察与审计 | M1/M2/M3 的限制来源、取消原因、通知尝试、审批与工单记录怎样查询和追溯？ | 结果要能验收，尤其多来源并存和跨模块失败 |

对“座位可约”使用**座位＋时间区间＋来源限制**的业务视角。实现表示可以在架构阶段选择，不预先规定数据库/服务拓扑。解除某一来源必须保留其他有效限制和开放条件。BP-06/07 的交接还需覆盖网络调用是否成功、失败重试与重复消息、先后顺序、恢复与补偿；课程要求模块间真实网络调用，不能只在同一库里改一个字段冒充集成。

## 四、并行开发、内部集成与整体交付

六人可按 M1/M2/M3/D 的责任和已确认契约并行实现 US，在内部持续集成并验证完整业务链路。例如：个人预约与冲突拒绝、签到超时取消与时段释放、整室审批对可约性的影响、教室/座位维修下架及验收恢复。它们是**系统联调与验收的覆盖路径**，不是排成几次对外交付的功能批次。剩余业务细项、团队责任和契约未确定时，相关工作保持阻塞；跨模块链路由有关小组共同验证。

持续维护三种不同状态：①业务规则/AC 是否已确认；②US 是否达到开工条件；③代码是否已实现并验收。新需求或决策按 `原因 → 影响 R/Q/BP/CAP/US/AC → 数据与契约 → 实现/测试 → 评审和版本` 记录，只修改受影响内容。统一交付前仍要持续验证代码；内部测试通过不等于系统整体验收。

## 六、交给接手 Agent 的具体任务

1. 先读本目录 `README.md`、课程任务书、`08`、本文件及 `00`～`06` 的 BP 原文；`07` 可作为待核对索引，现行协作指南可用于方法与分工。**不要读取文件名含“历史讨论”的两份文档作为分析资料**，它们仅供用户保留讨论记录。
2. 按原 BP-01～07 的顺序审查流程、边界和验收场景；BP-01～03、05～07 主线已审，原 BP-04 查看功能已并入 BP-03。继续 BP-07 的 Q-26/28 剩余细项，可结合 `11`；相关问题每次集中提出 3～5 项。
3. 核对已审 BP 的边界、AC 与跨 BP 规则，准备简洁的正式 V1 供需求负责人确认；决定已记录在 `08`，对应 BP 和 `07` 须一致。
4. 范围、规则、US/AC 经需求负责人确认后，发布正式需求基线 V1。此后由六人团队讨论分工、CAP→M1/M2/M3/D、数据归属、技术方案和跨模块契约，再开展开发与整体联调；Agent 不替团队宣称已决定。
5. 若用户指出文件错误，以修订需求和同步关联文件为任务，不只在聊天里解释。每次交付都区分“已分析”“已确认”“开发就绪”“已实现”“已验收”。

**交接完成的目标**：下一个 Agent 能基于任务书、用户决策和当前 BP 正文继续需求分析，提出可供需求负责人批准的 V1，以及六人可讨论的架构、协作开发与整体联调方案；不把历史的增量交付方案带入当前项目。
