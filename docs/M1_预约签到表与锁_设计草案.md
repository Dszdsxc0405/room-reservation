# M1 预约、签到与超时处置的数据和锁设计草案

> 状态：A/B 共同评审稿；A 已确认预约与违约表的基本结构、三张协调锁表的实现方向，以及所有来源取消经 M1 统一入口和预约行锁；B 及相关模块尚待复核，尚无迁移、数据库适配或跨模块验收。依据 [BP-01](00_BP-01_查询并预约_V1.md) AC-02/05/06/24/25、[BP-02](01_BP-02_签到提醒与未签到处置_V1.md) AC-07～10/30～34、[M1 规则](rules/M1.md)、[内部模块调用契约](16_内部模块调用契约_V1.md)。B 工作目录的最新需求修订尚未合入本分支。

## 1. 已确认的业务规则

- **R-01 签到时点**：以 M1 取得该预约行独占锁后记录的服务端 `accepted_at` 为准，按整秒判断。15:15:00 受理仍在窗口；15:15:01 受理已超时。HTTP 到达时间不决定业务结果；未提交的尝试重试时重新受理。
- **R-02 编码日期**：验证预约教室在**预约使用日**的编码。00:00 开始的预约在前一日 23:55 提前签到，仍用预约使用日编码。编码的生成与验证接口由 E 负责。
- **R-03 延迟超时**：截止后无有效签到，即使定时任务延迟，也须补做一次超时取消、违约和通知。后来报修不能把这次违约改成免违约取消；报修免违约适用于尚未超时的预约。
- **R-04 取消与再约**：预约终止只用“取消”；其他原因取消不记未签到违约。取消后再约、历史再订均创建新预约，按当前条件重新校验，不复活旧 `booking_id`。
- **R-05 草案边界**：以上口径由需求负责人确认；B 独立工作目录仍按旧入口时间实现，需同步。本稿细化 M1 数据与锁；不决定 D 的编码生成或消息记录实现。

**数据库访问边界**：M1、M2、M3、D 是同一个 Spring Boot 应用内的业务模块，共用数据库连接与事务。各模块的 Repository 只写自己负责的表；M3 等模块通过 M1 的公开接口请求取消预约，D 通过自己的接口保存编码、主数据和消息事实。D 不充当所有业务表的 SQL 代理。

## 2. A：预约数据与共同锁

### 数据规则

| 编号 | 规则 |
|---|---|
| A-01 | `m1_booking` 的身份与时段：`booking_id`、`student_id`、`room_id`、`seat_id`、`starts_at`、`ends_at`、`use_local_date`、`created_at`。 |
| A-01a | 同表的状态与处置：`status`；可空的 `checked_in_at`、`cancelled_at`、`cancel_reason`、`cancel_source_type`、`cancel_source_id`。A 定预约基础字段；B 在**同一行**写签到或超时取消。字段名与 SQL 类型待迁移评审。 |
| A-02 | `room_id`、`starts_at`、`ends_at`、`use_local_date` 创建后不可原位修改。`room_id` 和使用日是创建时从 D 事实取得的快照；新约仍须重读 D 当前事实。 |
| A-03 | `status` 只有有效、取消。过了结束时点的历史预约可保持有效。`checked_in_at` 是签到事实；已签到预约后来仍可能因整室批准等原因取消。`cancel_reason = NO_SHOW` 时 `checked_in_at` 必须为空。 |
| A-04 | `m1_no_show_violation` 以 `booking_id` 同时作主键和预约外键，保存 `occurred_at`；学生从预约关联取得。只有超时取消同事务插入。若外部接口确需独立违约编号，由 A/B/F 复核后增补。 |
| A-05 | PostgreSQL 对**有效**预约的 `[starts_at, ends_at)` 建两条排斥约束：同座位不重叠、同学生不重叠。另约束 `starts_at < ends_at`、取消字段与状态一致，并索引到期扫描、本人历史和违约查询。取消后不再占用原区间。 |
| A-06 | 预约提交仍在事务内重验 D 资格、资源、开放、时长和 M1 限制；排斥约束是并发兜底。历史再订使用新 `booking_id`，走同一提交路径。 |

### 锁规则

| 编号 | 规则 |
|---|---|
| A-07 | A 选择由 M1 维护 `m1_room_coord_lock`、`m1_student_coord_lock`、`m1_seat_coord_lock`，分别承载教室共享/独占、学生独占、座位独占锁。每资源一行并幂等初始化；具体 SQL 和并发效果须经迁移评审与数据库测试。D 不直接写这些表。 |
| A-08 | 新约取锁：教室共享 → 学生独占 → 座位独占 → D 必要事实读锁 → 重验并插入。整室批准及教室级限制取教室独占；座位级报修/注销在教室共享后取座位独占。跨资源按稳定 ID 顺序取锁。 |
| A-09 | A 确认所有来源取消均经 M1 的同一公开写入入口；**所有修改既有预约的路径**都在同一 `m1_booking` 行上取独占锁，并在锁内重读状态。先取所需协调锁及 D 事实锁，后取预约行锁；多笔预约按稳定 `booking_id` 顺序处理。不得持有预约行锁后反向等待教室或 D 事实锁，也不得为一笔跨模块命令另开 `REQUIRES_NEW`。 |
| A-10 | B 的 `withLockedBooking` 只收到预约 ID。数据库适配可先无锁读取不可变的教室和使用日定位资源，按 A-08/A-09 取锁后重读核对。一次回调须在一个事务内完成并持锁至提交。到期批量扫描仅给候选 ID，逐笔事务重验；不可先用 `FOR UPDATE SKIP LOCKED` 锁预约行再取教室锁。 |
| A-11 | 签到、超时和所有来源取消均共用 A-09 的预约行锁；在锁内按当前预约事实决定结果。不增加未决签到表或进程内队列。 |

## 3. A/B：受理时点与竞态

| 编号 | 规则 |
|---|---|
| AB-01 | 先取得所需的 M1 协调锁与 D 事实锁，再取得预约行独占锁。签到在预约行锁内读取服务端当前实际时间为 `accepted_at`，按整秒判断窗口；不能使用事务开始时间或浏览器时间。 |
| AB-02 | 截止秒内到达 HTTP、但在下一秒才取得预约行锁的签到已超时。签到与超时、报修等写入按同一预约行锁串行；锁内重读状态，不能既签到成功又因未签到记违约。 |
| AB-03 | 取得行锁前的中断或锁等待失败是可重试的技术结果；未提交的尝试按新的受理时点重判。已提交但响应丢失时查询持久结果，不能重复签到、取消或记违约。 |
| AB-04 | M2/M3/D 跨模块命令仍按内部契约，每次未提交的尝试在取得 M1 协调锁后重取 `decisionAt`；报修是否已到截止还须在预约行锁内以实际当前时间复核。定时任务从截止后一秒起扫描，锁内重验到期与状态；延迟任务由恢复扫描补做。 |
| AB-05 | 编码事实若需要 D 行锁，必须在预约行锁前取得；若 E 确认校验无锁且事实在本次事务内稳定，才可在预约行锁内调用。E 确认接口及事实稳定性。 |

## 4. B：签到、提醒和超时处置

| 编号 | 规则 |
|---|---|
| B-01 | 按 AB-01 取得 `accepted_at`，截到整秒后，签到窗口为 `>= starts_at - 5 分钟` 且 `< starts_at + 15 分钟 + 1 秒`。锁内确认本人、预约有效、未签到及预约使用日编码有效；成功把受理时点写入 `checked_in_at`。现有预约因 D 变更被保留时，不再用“能否新约”规则拒绝签到。 |
| B-02 | B 当前在 `withLockedBooking` 回调内调用 `DailyRoomCodeVerifier`。若 E 校验会取 D 行锁，须先取得稳定的编码事实再锁预约行；只有 E 确认验证无锁且事实稳定时，才能保留回调内调用。 |
| B-03 | 超时任务在 `starts_at + 15 分钟 + 1 秒` 起扫描；取得教室共享锁和预约行锁后重验实际时间、状态及签到事实。仍有效且未签到时，在**同一事务**取消、插入唯一违约、保存 D 待投递取消消息。重复扫描或任务重跑不得重复这些结果。 |
| B-04 | 到期扫描不能替代锁内重验。任务延迟时，恢复扫描及后续需要释放或处置该预约的写入应先补做超时，再判断新约或来源操作。补做的超时取消是否计入后来报修来源的 `cancelledBookingIds`，由 A/B 与 M3 复核后定稿。 |
| B-05 | 开始前 15 分钟、开始后 10 分钟两次提醒分别去重。10 分钟提醒按 A-09 取锁并重验有效且未签到，只保存一次待投递事件。投递在事务提交后执行，失败不回滚取消或违约。 |

## 5. 其他模块：接口和来源取消

| 负责人 | 必须确认的规则与产出 |
|---|---|
| C（M2） | **C-01** 核对整室终审只取消冲突的未来有效个人预约；确认教室协调锁、多笔预约锁序、来源结果与重试。若现行接口足够，记录评审结论。 |
| D 成员（M3）与 A/B | **D-01** 报修在预约未超时且已开始未签到时取消而不记违约；若已超时且无有效签到，先补超时取消、一次违约及通知，再施加报修限制。**D-02** A 已确认报修取消经 M1 统一入口和预约行锁；跨模块契约已写入此业务结果，M3 负责人继续核对签到与报修交错、`cancelledBookingIds` 返回值，并签认 [跨模块接口](14_跨模块接口_V1.md)和[内部契约](16_内部模块调用契约_V1.md)。 |
| E（D 编码与主数据）与 B | **E-01** 定预约使用日编码校验接口、跨日规则、编码事实的稳定性和取锁方式。验证不能在 M1 预约行锁后再等待 D 事实锁；B 据此调整调用位置或端口。 |
| F（D 站内消息）与 B | **F-01** 同事务保存待投递记录，提交后投递；失败留尝试记录并重试。**F-02** 唯一事件键至少含 `businessOperationId + stepId + eventType + subjectType + subjectId + recipientId`；超时取消由预约 ID 和 `NO_SHOW`、提醒由预约 ID 和提醒阶段派生稳定编号。确认 D 记录能否满足 AC-07/33 的查询证据。 |
| 需求负责人 | **R-06** 已确认“预约行锁内受理时点”取代原 HTTP 入口时点；后续若变更可观察结果，再按需求决策流程同步文档。 |
