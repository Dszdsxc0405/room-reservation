## 2. 首轮最小架构要回答的六个问题

| 决策 | 为什么首轮必须说清 | 可交付的最短记录 |
|---|---|---|
| 预约、座位/教室主数据、整室限制、维修限制分别由谁维护 | 六人若各自修改同一事实会产生冲突 | `CAP/对象 → M1/M2/M3/D → 维护人/评审人` 表 |
| 谁对“该座位此时段可约”的最终判断负责 | 查询、提交、释放和来源追溯需要一致语义 | 判断所需事实、规则归属、并发保护责任 |
| M2/M3 怎样把限制施加给 M1，解除时怎样保留其他限制 | 任务书明确跨模块状态写回；存在多来源并存 | 调用/事件的触发、标识、时段、成功/失败与重复处理契约 |
| 当前迭代的业务政策与 Q 范围 | Q-01/02/03/06/08 等会改变同一结果 | 你确认的政策；暂缓项写清影响 US 和演示边界 |
| 采用什么技术栈、工程结构及数据迁移方式 | 六个 Agent 需要相同运行和交付契约 | 简短方案比较、选定版本、最小脚手架与验证结果 |
| 如何集成、验证、部署与回退 | 课程要求早期可交付工程证据 | 网络调用验证、CI 门禁、测试环境部署、迁移回放与回滚路径 |

**可讨论的责任选项（不是建议你直接采纳）**：A. M1 负责预约与最终可约性判断，M2/M3 分别维护自己的占用/维修事实并按契约提供给 M1；D 负责约定的身份、空间主数据等。B. D 统一负责跨模块的时段限制与可约性，M1 负责预约提交，M2/M3 提供各自事实。比较两者时重点检查：写入一致性、D 的工作量与故障责任、是否能真实演示网络调用、六人是否能各自开发和测试。**先定事实的所有者，再定调用方式；不能只画模块方框。**

技术栈选型也只评估与本项目交付相关的项目：六人熟悉程度、从空库部署速度、接口/迁移工具、CI 与环境条件、跨模块网络调用、测试和回滚成本。任务书允许自选栈，但不允许仅凭 Agent 的首个推荐直接定案。

## 4. 后续迭代和变化如何受控

1. **当前轮**：你审查《01》《02》并裁决首轮 Q；六人据此比较模块与技术方案，形成 `architecture.md` 初版、D 归属决策及首轮接口/数据契约。只有就绪的 US 分配给开发者/Agent。
2. **开发并行**：BP-02 等继续深入分析。每发现新事实，做一次小型影响记录：`新证据 → 涉及 BP/CAP/US/AC/契约 → 现有设计是否冲突 → 谁决定 → 需重做什么`。
3. **处理影响**：若仅补后续生命周期，补关联与测试；若改变行为或契约，暂停受影响 US，决策后同时修订需求、架构、代码和验收；若新结论未知，创建 Q 并标明阻塞范围。
4. **记录与交付**：文档与代码经同一版本库合并请求审查，记录决策及替代方案；运行 AC、跨模块集成和迁移测试，写可定位的证据。已实现、已验收分别标状态；已验收故事被改动时重新打开并重验。

例子：BP-02 深入分析后发现未签到取消后的余下时段还可以再次预约。若这与初版“每个时段只存一次永久占用”的数据设计冲突，就不是 BP-02 单独补一段文档：要回查 BP-01 的可约性规则、预约数据模型、AC、API 和迁移，提出变更并重验。反过来，如果初版已经按**有效占用事实**判断，并能移除个人限制同时保留整室/维修限制，可能只需要补 BP-02 的 AC 和接口实现。

## 5. 检验“可控”的证据，而非零返工承诺

首轮 Review 可以用以下证据检验此方法：

| 想验证什么 | 可观察证据 |
|---|---|
| 没有偷定业务政策 | Q 的状态、决策人、受影响 US；未决项仍在表里 |
| 架构先于正式实现且可修订 | 模块/D 归属、技术选型、接口契约的短决策记录及版本历史 |
| 并行开发没有各写一套规则 | 同一来源定义；跨组评审；契约测试与网络集成演示 |
| 后续 BP 影响能被定位 | 影响记录指向 BP/CAP/US/AC、契约、测试和负责人 |
| 功能完成有证据 | AC 的行为测试及人工验收、迁移回放、构建/部署记录与版本标记 |

**失败信号**：某 US 标“已完成”但 Q 未决定、接口无所有者、AC 没有可观察结果，或代码改变了规则而文档和测试仍称“已验收”。这比追求“未来绝不返工”更能实际检验过程是否可控。
