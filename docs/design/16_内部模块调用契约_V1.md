# 内部模块调用契约 V1（待模块复核）

> 2026-11-19 起草。细化[跨模块接口 V1](14_跨模块接口_V1.md)中 M2/M3/D 对 M1 的写入及各模块对 D 的读取；不增加用户可观察的业务规则。依据[需求基线](../business/07_需求基线_V1.md)、[决策记录](../business/08_业务决策记录_V1.md)、BP-01/03/05/06/07 和[数据归属](12_六人分工与数据归属_V1.md)。这是**同一个 Spring Boot 应用内的 Java 接口**，不是四个服务之间的 HTTP API；方法名和 DTO 名为建议，语义、归属和失败处理是复核重点。尚无实现或验收结果。

## 1. 通用类型、时点与结果

| 类型 | 字段及约束 | 用途 |
|---|---|---|
| `OperationId` | `businessOperationId`（外层业务命令 ID）和 `stepId`（由目标模块、动作、目标业务对象 ID 稳定生成）；重试保持不变，不用批量列表下标 | 两字段合起来唯一标识一次跨模块副作用；同一编号换操作意图须拒绝 |
| `SourceRef` | `sourceType`（`M2_APPROVAL`、`M3_REPAIR`、`D_ROOM_PLAN`、`D_SEAT_RETIREMENT`）和所属模块内的 `sourceId` | 来源类型同时确定所属模块与业务含义；不同类型可使用相同局部 ID，只有所属模块能施加或请求解除 |
| `ResourceRef` | 明确区分 `RoomRef(roomId)` 与 `SeatRef(roomId, seatId)`；D 确认座位属于该教室 | 用类型表达资源粒度，不另传 `resourceKind` 或可空座位 ID |
| `TimeRange` | `startInclusive`、`endExclusive`，均为绝对 `Instant`，`start < end`；业务本地日期及整点规则用 D 的学校时区校验 | M2 批准的有限时段，按 `[开始, 结束)` 相交 |
| `ActorRef` | `actorId`、`actorKind`（用户/系统任务）；仅系统任务代用户执行时另带 `initiatingUserId`，直接用户操作不重复填写 | 审计和消息来源；不携带可直接信任的角色结论，权限由 D 当前事实核验 |
| `OperationOutcome<T>` | `OperationId`、`SourceRef`、动作、结果值及 `recordedAt`；仅在外层事务提交后对其他事务可见 | M1 持久化已完成的副作用结果，供响应丢失后的查询与去重；事务内方法返回值仍以外层提交为准 |

每次**未提交的尝试**在取得协调锁后，由服务端重新取得统一 `decisionAt`；学校本地自然日和开放时间使用 D 的学校时区，不信任浏览器时钟。`decisionAt` 及由“立即生效”推导的时点不是固定重试负载。重试固定的是 `OperationId`、`SourceRef`、资源、用户选择的未来时段、操作者和动作意图；若前次已提交，直接返回持久结果，若前次回滚则用新时点和当前事实重新判定。结果至少保存到业务源记录可追溯期间，不能因为缓存过期重复执行。

`SourceRef + action` 也须有唯一约束，防止换 `stepId` 重复施加同一来源或重复解除。换编号但来源与固定操作意图完全相同时返回原结果；同一来源再次施加但资源、时段或范围不同，返回 `SOURCE_CONFLICT`。修改来源内容须由所属模块定义显式修订操作，本稿不定义隐式覆盖。解除操作只针对原 `SourceRef`；解除不存在或未确认生效的来源返回 `SOURCE_NOT_ACTIVE`，不能视为解除其他来源。已解除来源不可因迟到的施加重试重新生效。M3/D 引发整室批准取消时，由 M2 先修改自己的批准状态，再由 M2 请求解除其 `M2_APPROVAL` 来源；M3/D 不冒用该来源。

错误以稳定代码返回，内部异常保留给日志；调用方不能把技术失败映射成“资源可用”或“审批通过”。

| 代码 | 含义与调用方动作 |
|---|---|
| `INVALID_ARGUMENT` | 缺字段、区间无效、资源与来源类型不匹配；修正命令，不自动重试 |
| `RESOURCE_NOT_FOUND` / `SOURCE_NOT_ACTIVE` | D 无此资源，或 M1 无可解除的活动来源；业务拒绝并核对源记录 |
| `PERMISSION_DENIED` | D 当前授权不允许发起操作；拒绝，不靠前端权限或旧快照放行 |
| `NOT_ELIGIBLE` | 当前开放、资格、报修或管理限制不允许整室终审；M2 不得标记批准，给出可追溯原因 |
| `SOURCE_CONFLICT` / `OPERATION_CONFLICT` | 相同来源或操作编号出现不同有效负载；数据/调用错误，告警并人工核查 |
| `CONCURRENT_CHANGE` | 事务重验时源状态或配置已变化；回滚，按当前事实重新决策；不能把旧审批直接重放成成功 |
| `RETRYABLE_FAILURE` | 锁等待、数据库暂不可用等；查询持久结果后重试同一命令 |
| `IN_PROGRESS` | 同编号事务仍在执行或等待锁；仅为临时响应，等待或重查持久结果，不作第二次取消/通知 |

`NOT_ELIGIBLE` 是当前业务状态拒绝；`RETRYABLE_FAILURE`、`IN_PROGRESS` 不是业务驳回。HTTP 层到提示文案的映射后续单独设计。

## 2. M1 对 M2/M3/D 的写入接口

建议由 M1 发布 `SeatRestrictionPort`。调用方只可通过它改变 M1 的限制、个人预约和取消事实，不能直接修改 M1 表。`apply` 与 `release` 均须在调用方业务命令的同一数据库事务中执行（第 4 节）。

```java
RestrictionEffect apply(ApplyRestriction command);
ReleaseEffect release(ReleaseRestriction command);
Optional<OperationOutcome<?>> findOutcome(OperationId id); // 仅查已提交结果
```

| 命令 | 必填参数 | M1 成功结果与拒绝条件 | 依据 |
|---|---|---|---|
| `M2_APPROVAL` 施加 | `OperationId`、`SourceRef(M2_APPROVAL, applicationId)`、`RoomRef`、`approvedRange`、`ActorRef` | 确认时段尚未开始，且在同一教室协调锁下没有已生效的报修/关闭限制；记录该申请来源的全室时段限制，取消相交的**未来**有效个人预约；已取消者不记违约。不能覆盖现有报修/关闭而批准。 | BP-06 AC-18/29；BP-01 AC-04/26 |
| `M3_REPAIR` 施加 | `OperationId`、`SourceRef(M3_REPAIR, workOrderId)`、`RoomRef` 或 `SeatRef`、`ActorRef` | 从报修命令提交时起，对全室或单座位限制新约；取消相交的未来个人预约，以及**已开始但尚未签到**的个人预约；保留已签到且正在使用的预约至原结束。其他限制不妨碍本工单来源施加。 | BP-07 AC-20/21；BP-01 AC-04 |
| `D_ROOM_PLAN` 施加 | `OperationId`、`SourceRef(D_ROOM_PLAN, planId)`、`RoomRef`、D 的不透明 `planRevision`、未来生效时点或 `IMMEDIATE` 意图、`ActorRef` | D 在本事务内提供计划覆盖判定；M1 记录计划来源，取消生效后受影响的**未来**个人预约，保留生效前及已签到正在使用的预约；已开始但尚未签到的预约保留到原签到截止时点，期间允许按原规则签到，签到后使用到原定结束，逾期未签到按通常规则处置。新约须同时通过 D 当前开放计划与 M1 其他限制重验。 | BP-03 AC-12；BP-05 AC-36 |
| `D_SEAT_RETIREMENT` 施加 | `OperationId`、`SourceRef(D_SEAT_RETIREMENT, changeId)`、`SeatRef`、未来生效时点或 `IMMEDIATE` 意图、`ActorRef` | 限制该座位后续新约，取消冲突的未来个人预约，已签到正在使用的预约可到原结束；已开始但尚未签到的预约按原窗口允许签到，逾期未签到按通常规则处置。M2 的整室安排不由本接口取消。 | BP-03 AC-12 |
| 来源解除 | `OperationId`、原 `SourceRef`、`ResourceRef`、`ActorRef`、`reason` | 只解除这一来源；返回解除的来源及生效时点，不恢复被该来源取消的个人预约。M2 批准被取消、M3 撤单/验收通过、D 撤销尚未生效的关闭/缩短计划分别调用。 | BP-01 AC-28；BP-06 AC-18/19；BP-07 AC-22；BP-03 AC-12 |

`RestrictionEffect` 至少返回 `SourceRef`、`ResourceRef`、`cancelledBookingIds`；`ReleaseEffect` 至少返回被解除的 `SourceRef`。`cancelledBookingIds` 用于核对结果、持久消息事件去重，调用方不得据此自行再修改预约。当前使用的结束时点仅由下文只读接口在进入维修中前重新查询，不在施加结果中返回易过期的副本。M1 负责把取消原因区分为整室批准、报修、管理计划、座位注销；这些取消一律不产生未签到违约。M1 在**同一事务**完成限制和取消，任何一步失败则两者一起回滚。

若对外结果需要 `committedAt`，它只能在外层事务提交后记录或查询；`apply/release` 返回给事务内调用方时不能提前声称数据库已经提交。报修的提交时点在本次成功尝试内取得；未提交的尝试回滚后重试，必须以新时点重新判定当前/未来预约及签到状态。

M2 终审若因当前报修/关闭或重叠批准被拒，应保留 M2 自己的审批状态规则：重叠批准按 BP-06 自动驳回；报修/关闭阻止批准，不得把 M1 的技术错误误写为审批人驳回。M3 报修施加与 D 管理计划施加不因已有 M2 限制而拒绝；它们仍须按[总契约](14_跨模块接口_V1.md)请求 M2 取消相交的未来整室批准和待审申请。座位报修/注销不取消整室安排，但要提供故障/注销座位提示。

M1 的只读端口另提供 `getProtectedUseEnd(resourceRef, at)`：返回受影响教室或座位当前已签到个人预约的最晚原定结束时点及预约 ID；无此使用返回空。M3 在进入维修中前于新事务重读此结果，并向 M2 查询正在使用的整室安排，取两者较晚结束时点；未到时不得进入维修中。D 管理查看使用 `getManagementBookingFacts(roomIds, useDateRange, requestingActorId, includePersonalDetails)`：返回预约、取消原因、签到、违约及预约使用日本地日期的分页事实，不在 M1 内重新写统计。M1 与 D 都须核验请求者对每个教室的当前查看权限；`includePersonalDetails=true` 仅允许该教室获授权管理员或系统管理员。无权限返回 `PERMISSION_DENIED`，范围和分页参数无效返回 `INVALID_ARGUMENT`；D 按 BP-03 AC-14 汇总，不能把分页后的局部事实当全量统计。

### D 计划覆盖判定

关闭可能长期有效，缩短开放时间可能按日重复，因此 `D_ROOM_PLAN` 不能只传一个固定结束时点。D 提供 `SourceRef + planRevision` 对应的不可变覆盖规则：给定某笔预约区间，返回它是否落在计划生效后且违反新可用性；M1 在事务内对已有未来有效预约逐笔判定并取消。对以后新提交的预约，M1 再读取 D 的当前有效配置和计划判断，不能仅靠一次性展开的短期限制表。修订标记与 D 保存的源记录必须一致；不一致返回 `CONCURRENT_CHANGE` 并回滚。具体覆盖规则的存储形式由 D/M1 联合评审。

## 3. 各模块读取 D 的接口

建议 D 发布只读 `ResourceFactsPort`、`PolicyFactsPort`、`AuthorizationPort`。返回值是不可变快照，包含 `version` 和读取的服务端时点；`version` 用于提交时重验，不是让页面或缓存长期持有的许可。读取失败时，M1 不得创建预约，M2 不得提交/批准整室申请，M3 不得接受报修或派工，D 管理操作不得越过授权检查。

| 接口及参数 | 返回的最小权威事实 | 使用方与重验时点 | 错误 |
|---|---|---|---|
| `getRoom(roomId, at)` | `roomId`、唯一编号、全校/院系归属、登记/注销状态、`version`；时段开放与关闭计划由 `getOpeningPolicy` 判断 | M1 查询和预约提交；M2 申请提交与终审；M3 报修提交；D 管理变更 | `RESOURCE_NOT_FOUND`、`RETRYABLE_FAILURE` |
| `getSeat(seatId, at)` | `seatId`、`roomId`、唯一编号、登记/注销/停用状态、插座标记、`version` | M1 查询、提交及签到关联；M3 座位报修；D 座位变更。必须核对 `roomId` | 同上，或 `INVALID_ARGUMENT`（所属不符） |
| `getOpeningPolicy(roomId, range, decisionAt)` | 学校时区、区间内开放/关闭判定、有效计划 ID/版本、是否符合开放时间、`version` | M1 每次预约最终判断；M2 提交及终审；D 保存计划时给 M1 覆盖判定 | `RESOURCE_NOT_FOUND`、`CONCURRENT_CHANGE`、`RETRYABLE_FAILURE` |
| `getDurationPolicy(kind, decisionAt)` | `kind` 为个人/整室，分别返回当前单次小时上限、`version`；初始 4/8 小时 | M1 创建预约；M2 申请提交及终审（待审按新上限重验）；旧有效预约/旧批准不追溯取消 | `RETRYABLE_FAILURE` |
| `getActorFacts(actorId, decisionAt)` | 用户的学籍/教职工身份、学生院系及 `version`；不返回管理员或维修员角色及教室授权 | M1 学生资格；M2 申请人范围；M3 报修人是否为学生的判断；各模块不得信任客户端自报身份 | `RESOURCE_NOT_FOUND`、`RETRYABLE_FAILURE` |
| `authorize(actorId, action, roomId?, decisionAt)` | 针对这一次动作及教室的 `allowed`、拒绝原因和授权 `version`；不重复返回完整角色/授权集合 | 在各模块**状态变更**前重验；M2 初审需该教室授权、终审需系统管理员；M3 派工/验收需该教室授权；D 管理查询也需检查 | 读取失败为 `RETRYABLE_FAILURE`；`allowed=false` 是正常授权结果，调用方转为 `PERMISSION_DENIED` |
| `evaluatePlan(SourceRef(D_ROOM_PLAN, planId), planRevision, bookingRange, decisionAt)` | 对指定预约区间是否受计划覆盖、计划当前有效/撤销状态及修订标记 | 仅 D 管理计划保存或撤销时由 M1 调用；不得由 M1 自行解释 D 的开放规则 | `RESOURCE_NOT_FOUND`、`CONCURRENT_CHANGE` |

学生预约的院系范围、整室申请的学生本院系/全校范围由 M1/M2 使用 D 的身份和资源事实判断；教职工整室申请范围按 BP-06。D 提供事实与授权结论，不替 M1/M2 判定座位占用、整室重叠、工单冲突。M2 的报修状态仍从 M3 读，不能用 D 主数据代替。查询页可用快照展示；提交、审批和派工等状态变更须在事务内重新读取 D，给相关身份、授权、资源与配置行加读锁直至提交，D 对这些行的变更取冲突写锁。先前查询的 `version` 变化时重新计算，不以旧结果放行。D 的纯读取端口不依赖 M1；D 发起跨模块写入的应用服务可依赖 M1 端口，避免互相注入形成循环。

## 4. 事务、并发及重复执行

1. **一个命令，一个本地事务。** M2 终审批准 = M2 审批结论 + M1 限制和取消；M3 报修提交 = M3 工单 + M1 限制和取消 +（教室工单）M2 申请处置；D 关闭/缩时计划保存 = D 计划 + M1 处置 + M2 处置。上述写入在同一个 PostgreSQL 事务内提交或回滚，模块方法加入外层事务，不另开 `REQUIRES_NEW`。报修工单、计划、终审在全体必需结果提交前不能对用户显示最终成功。
2. **协调锁先于业务行锁。** 同一教室的新约、整室终审、教室报修和关闭/缩时计划先通过 M1 的教室协调锁：个人预约取共享锁，整室批准及教室级限制取独占锁。个人预约接着取 M1 的学生独占锁、座位独占锁，再检查本人及座位占用；同一学生对不同教室或座位的并发提交因此串行化。座位报修/注销在教室共享锁后取座位独占锁。数据库对“学生+重叠时段”和“座位+重叠时段”的约束仍作最终保护。其后按固定顺序锁定 D 的身份/授权、资源、配置行，再处理 M2/M3 源状态及 M1 预约/限制。一个命令涉及多个教室或座位时，按稳定 ID 顺序取锁；不能先持有 M2/M3/D 业务行锁再等待 M1 教室锁。具体 SQL 锁模式由实现评审确认，接口测试须验证死锁与竞态。
3. **提交前最终重验。** M2 在协调锁内重验申请仍待终审、当前审批权限、D 开放与整室上限、M3 教室报修、其他已批准整室；M3 在协调锁内重验资源、报修权限和同资源未结束工单；D 在协调锁内重验管理权限和计划修订。M1 对新预约在锁内重验 D 资格/开放、本人和座位占用及全部有效来源。D 撤权、院系/资源修改和时长/开放配置写入须与上述 D 读锁使用相冲突的写锁；同一事务持锁至提交。纯 D 授权或时长变更不必取 M1 教室锁，但必须遵守 D 行锁顺序；影响预约/整室安排的 D 计划先取 M1 教室锁。以事务提交顺序落实“先完成的操作生效”：若终审先提交，后续报修/关闭取消批准；若报修/关闭先提交，终审无法批准。
4. **幂等与恢复。** 操作结果、固定操作意图摘要、来源状态及待发送消息事件与业务写入同事务持久化，并对 `businessOperationId + stepId`、`SourceRef + action` 加唯一约束。摘要不包含每次尝试重取的 `decisionAt`、由 `IMMEDIATE` 推导的时点或从 D 重读的 `planRevision`；未来生效的用户指定时点则属于固定意图。同编号同意图重复调用返回原结果和原 `cancelledBookingIds`，不得重复取消、记违约或生成消息；同编号不同意图返回 `OPERATION_CONFLICT`。例如教室报修整体只有一个 `businessOperationId`，但 M1 施加、M2 取消多笔批准、M1 逐笔解除批准来源各有固定 `stepId`，其中逐笔步骤由申请 ID 派生。事务提交前进程中断则全体回滚；提交后响应丢失则 `findOutcome` 找到最终结果。另一事务仍在执行时可临时返回 `IN_PROGRESS`，但本方案不另行提交持久“处理中”记录；查询只返回已提交结果，未查到结果仍须处理可能存在的在途事务，再以原编号重试。若未来改为分步事务，须另行评审持久恢复状态机、重试期限和来源补偿，不能沿用本节的原子性假设。
5. **通知与审计。** M1/M2/M3 决定消息对象、内容和业务时点；D 在上述事务内保存带事件键的待投递记录，实际站内投递在提交后执行。事件键至少由 `businessOperationId + stepId + eventType + subjectType + subjectId + recipientId` 组成，`subjectId` 是被取消的预约/整室申请等具体对象 ID；同一人被一次命令取消多笔安排时每笔均有独立消息。失败记录并重试，不回滚已确认业务结果；审计记录按操作编号及业务对象去重。通知不可在未提交前直接产生不可回滚的外部副作用。

## 5. 联调矩阵与待复核点

| 场景 | 应见结果 | AC |
|---|---|
| 终审与个人新约并发；终审与教室报修/关闭计划交错 | 不漏取消、不留下获批与报修/关闭同时可新约的状态；按先提交者决定后续动作 | AC-04/18/21/29/36 |
| 同一施加/解除编号重复、换编号重复来源、响应丢失后重试 | 相同结果、无重复取消或通知；负载冲突明确报错 | AC-18/21/22/28 |
| 事务中 M1 或 M2 失败；D 计划版本变化；通知投递失败 | 前三者整体回滚或保持待恢复，不能显示成功；通知失败不改业务结果 | AC-12/18/21/33/36 |
| D 院系、开放时间、时长上限或授权在查询后改变 | M1/M2/M3 提交或状态变更时使用当前事实；旧批准和旧个人预约按 BP 保留 | AC-06/15/16/17 |
| 解除整室、报修或计划中的一个来源 | 其他有效来源仍限制新约，已取消预约/申请不自动恢复 | AC-18/19/22/28 |
| 同一学生同时预约不同座位；撤销审批权限与终审交错 | 学生最多一笔重叠预约有效；终审在提交时仍持有有效授权，否则失败 | AC-16/25 |
| 报修首次尝试在签到截止前回滚、截止后重试；一次计划取消同一学生两笔预约 | 重试使用新服务端时点和当前签到/违约事实；两笔取消各生成独立通知 | AC-09/21/30/33/36 |

**已确认的 D 边界：** 需求负责人决定，D 立即关闭/缩短开放或注销座位时，已开始但尚未签到的个人预约保留到原签到截止时点；期间可凭预约教室当天有效编码签到，签到后使用到原定结束；逾期未签到按通常规则取消并记一次违约。M1 的签到校验不得仅因 D 当前限制新约而拒绝这笔既有预约；新预约仍须按 D 当前条件拒绝。M3 报修继续按 BP-07 AC-21 立即取消已开始未签到预约，不适用此保留规则。

**模块复核：** M1（A/B）确认锁协议、限制覆盖和取消结果；M2（C）确认终审/解除与报修交错；M3（D）确认报修时点及当前使用；D（E/F）确认数据快照、计划判定、授权及消息去重。本文不定义数据库表名或 Web HTTP 错误码；这些在接口语义确认后由所属模块设计。
