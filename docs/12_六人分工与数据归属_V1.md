# 六人分工与数据归属 V1

> 2026-11-06 经需求负责人确认。成员 A～F 是临时代号，六人均为全栈工程师；实际成员认领和组内达成一致的过程仍须记录。本稿确定责任，不预定技术栈或数据库拆分。依据：[需求基线 V1](07_需求基线_V1.md)和[课程任务书](Pj-任务书.pdf)。

## 分工

| 成员 | 主责 | 配合与评审 |
|---|---|---|
| A | M1：座位查询、预约、最终可约性判断、限制来源记录 | 与 C、D 核对整室和报修写回 |
| B | M1：签到、提醒触发、超时取消、违约与历史再订 | 评审 A 的并发预约；对接 F 的通知能力 |
| C | M2：整室申请、两级审批、48 小时超时与撤销 | 与 A 核对座位占用；与 E 核对教室资格和开放时间 |
| D | M3：教室/座位报修、派单、维修、超时、验收与评价 | 与 A 核对预约限制；与 C 核对整室申请的取消 |
| E | 公共层 D：教室/座位主数据、配置管理、开放时间、角色与权限 | 对接 M1/M2/M3 的查询及管理变更；评审 C |
| F | 公共层 D：站内消息、操作审计、运营管理查询与统计；牵头构建和部署流水线 | 对接所有业务模块；评审 D |

已确定 **M1 两人、M2 一人、M3 一人、D 两人**。D 有明确开发者；C、D 的业务工作分别由 E、F 配合和交叉评审。若实际工作量不均，六人可在确认接口后提出调整，再记录决定。

## 数据主责

| 业务事实 | 唯一修改方 | 其他模块怎样使用 |
|---|---|---|
| 教室、座位、院系归属、登记状态、开放时间、时长上限、角色权限等配置 | D（E） | M1/M2/M3 通过 D 的接口读取；管理变更由 D 发起跨模块处置 |
| 个人预约、签到、违约、座位时段限制及其来源、最终可约性 | M1（A/B） | M2/M3/D 调用 M1 公开接口写入或解除本来源，不直接修改 M1 数据 |
| 整室申请、审批及其状态 | M2（C） | M1/D/M3 通过 M2 接口读取或发起有权限的取消 |
| 报修工单、维修状态、验收与评价 | M3（D） | M1/M2/D 通过 M3 接口读取；不直接改工单 |
| 站内消息投递记录、操作审计 | D（F） | 业务模块决定通知对象、内容与触发时点，D 负责投递及记录 |
| 运营管理查询与统计 | D（F） | 通过 M1 等模块公开接口读取源数据；统计结果不替代业务源记录，个人详情按授权范围展示 |

## 必须设计的交接

- **M2 → M1：**整室终审通过时写入该来源的整室限制，并按 V1 取消冲突的未来个人预约；批准取消时只解除本来源。
- **M3 → M1/M2：**按 V1，报修提交时限制受影响座位新约、取消未来个人预约；教室报修同时取消未来整室批准和待审申请。维修中只开始 72 小时计时；验收或维修前撤单后解除本工单限制。
- **D → M1/M2：**保存未来关闭或缩短开放时间计划时，按生效时段处置个人预约、整室批准和待审申请；只注销单座位时保留整室安排并提示该座位不可用。
- **各业务模块 → D：**业务模块决定何时、通知谁、通知什么；D 投递站内消息并记录结果。
- **D 运营管理 → M1：**查询授权范围内的个人预约、签到与违约事实，按 V1 口径计算预约量、取消数、签到量、违约量和签到率。

技术与接口设计见[技术方案 V1](13_技术方案_V1.md)和[跨模块接口 V1](14_跨模块接口_V1.md)。任务书以“维修中”写回为例；需求负责人已明确本系统在**报修提交时**生效，接口契约按 V1 执行。
